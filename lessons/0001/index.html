Lesson 0001 · 全局地图

全局地图:27 个技能,一条流水线

27 个技能,一张地图:一条从想法到复盘的流水线,加每个技能在图上的位置。学完它的检验标准只有一个——任何情境,10 秒内说出该用哪个技能。

本课目标:学完你能做什么。 面对任何一个工作情境,10 秒内说出该用哪个技能。这节课练的就是这个路由能力。

一个心法:流程就是 agent 的记忆

Matt Pocock 的出发点是:你手边有一群「中等到良好」的工程师(agent),它们有个致命缺陷——没有记忆。不记得做过什么,每次都是新的。所以你不能靠默契,只能靠极其明确、每次都一样的流程来让它们干出有用的活。skills 就是把流程写下来,让 AI 每次都走同一条严格的路。(来源:5 agent skills I use every day)

这句话解释了整套体系的设计:为什么先访谈再写 spec,为什么 spec 要拆成工单,为什么实现必须测试先行——每一步都是在给没有记忆的工人补上「上次说到哪了」。

主流程:idea → ship 的六步

这是整套体系的主干。每个技能吃进上一步的产物,吐出下一步的原料:

  1. /grill-with-docs

    把你访谈到共识为止(每次 grilling 可能 16~50 个问题),决策顺手沉淀进 GLOSSARY.md / ADR

  2. /to-spec

    把已达成的共识写成 spec(含 user stories),发布到 issue tracker。注意:它不再访谈你,访谈在上一轮已经完成

  3. /to-tickets

    把 spec 拆成 tracer-bullet 工单:每张都是打通所有层的薄竖切片,并声明 blocking 关系,可以多 agent 并行认领

  4. /implement

    按工单写代码:内部驱动 /tdd(红-绿-重构),收尾自动跑 /code-review。工单多想一次跑完?批量化路线 /implement-spec 见工程一章

  5. /code-review

    两轴审查:Standards 轴(代码规范 + Fowler 坏味道基线)与 Spec 轴(是否忠实实现来源 spec),并行子 agent 执行

  6. /retro

    复盘这次会话:不评代码,评环境——把它踩过的坑变成导航指针、自动检查、标准的改进,下次会话少踩一遍(v1.3 新增的第六步)

流程顺序来源:aihero.dev/skills The Main Flow; 各步骤细节来源:5 agent skills I use every day 与 Skills changelog v1.3。

主流程底下:参考层 Reference

有五个技能你很少直接敲,它们是被上面调用(或在你开 PR 时自动进场)的公共层:

  • /tdd — 被 /implement 驱动
  • /grilling — 被 /grill-me、/grill-with-docs 等一切访谈类技能复用
  • /domain-modeling — 被 /grill-with-docs 调用,同步维护 GLOSSARY.md 和 ADR
  • /codebase-design — deep module 的共同词汇,贯穿全部
  • /pr — 写 PR 正文时被模型拉进场,定下「摘要图 + 前后证据 + 合并危险」的骨架(v1.3 新增)

这意味着:当你直接用 /grill-me 时,实际运行的是 /grilling 的方法;当你 /implement 时,内部走的是 /tdd。理解这一点,你就明白为什么文档说「参考层是被其他技能调用的可复用层」。(来源:本地插件 engineering/README.md,见 GitHub 仓库)

主流程周围:三个按需进入的模块

Shaping — 把不确定变成决策

主流程走到一半发现「这个问题还没答案」时进来。入口是 /wayfinder:把大工程铺成一张决策地图,逐个解决,答案回流主流程。

  • /wayfinder
  • /prototype
  • /research

Engineering — 保养仓库,批量施工

v1.3 起由 Upkeep 更名而来。一半保养流程的原料——工单池不堆烂票,代码库不积烂账;另一半为流程生成工作:一个 spec 一次并行施工。

  • /improve-codebase-architecture
  • /diagnosing-bugs
  • /triage
  • /wizard
  • /implement-spec(v1.3 新增)

Productivity — 人自己的工作流

与代码无关:访谈(/grill-me)、交接(/handoff)、问卷(/to-questionnaire)、教学(/teach)、没读懂的消息(/wait-what)。

  • /grill-me 等 6 个

v1.3 的两处地图变化。 其一,旧地图上的 /resolving-merge-conflicts 被移除:冲突处理被视为 harness 层的活,agent 现在自己会解,不再需要专门技能——遇到冲突直接让 agent 处理即可,「先读懂两个意图再让路」的思路仍然成立。其二,文件 CONTEXT.md 全面更名为 GLOSSARY.md(词汇表名副其实;迁移就是一条 git mv,见 0002)。

一个必须记住的二分:user-invoked vs model-invoked

engineering 和 productivity 两个 README 把技能分成两类:

类型怎么触发例子
user-invoked只有你主动敲 /技能名 才会运行,模型不会自己拉进来/grill-me、/to-spec、/implement、/retro、/ask-matt
model-invoked模型可以根据语境自己触发,你也可以手动敲/tdd、/prototype、/research、/code-review、/pr

推论:主流程的骨架(访谈→spec→工单→实现→审查)几乎全是 user-invoked——节奏由你掌握。你不说,agent 不会擅自开始写 spec。

练一练:情境路由

下面 7 个情境,凭第一反应选技能。答错没关系——错的地方就是要补的缝。

得分 0 / 8

  1. 1. 你脑子里有个新特性想法,但边界、取舍都还没想清。

  2. 2. 你和 agent 刚就方案达成共识,要把结论落成书面规格。

  3. 3. spec 写好了,要拆成几个 agent 能并行认领的小块工作。

  4. 4. 工单就绪,要开始真正写代码了。

  5. 5. diff 已经完成,提交前要对照规范和原始 spec 各查一遍。

  6. 6. code-review 通过了。这次会话踩了不少坑:绕远找文件、被 linter 逮住低级错。你想让这些教训变成仓库的长期改进,该敲哪个?

  7. 7. 这个项目要做的事太大,一个 agent 会话根本装不下。

  8. 8. 一条消息(PR 描述、同事回复)你看了两遍还是没懂。

已答 0 / 8 题。

合上页面,回忆一遍

测验做完后,做一次不看资料的回忆(这是让记忆长存的检索练习,比重读有效得多):拿一张纸,画出主流程五步,并给每步标注「输入 → 产物」。画完再对照速查图检查。

间隔安排:第一次学完后的第 1、3、7 天各回来重做一次上面的测验。每次 2 分钟,这比一次学一小时更能把路由能力焊进长期记忆。

首读材料

5 agent skills I use every day —— Matt Pocock 亲述主流程上最核心的五个技能,15 分钟。本课的心法和流程细节几乎全部出自这里,值得读原文。想追本图最新的变化(第六步 /retro、工程模块批量施工、GLOSSARY.md 改名),读 Skills changelog v1.3。

卡住了怎么办。 哪个路由拿不准、哪两个技能分不清区别,先查词典或全局地图; 还不清楚,到仓库 issue 区提出来。
