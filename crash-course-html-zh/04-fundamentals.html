你的起点上下文（Your Starting Context）

如果你跟完了前面的概念部分，甚至动手做完了代码练习，你可能已经注意到：我对自己的 context window（上下文窗口）里到底装着什么，时刻都抱有一种强烈的偏执。

构建 AI 应用时，你必须对放进 context window 的每一个 token 都格外小心，才能确保应用高效运行、并通过你的评测。我继承了这种 context 偏执，并把它带进了 agent 编码。

# 消灭 bloat（Killing Bloat）

消灭 bloat：理解你的 agent 载荷（Killing Bloat: Understanding Your Agent's Payload）

你发给 agent 的每一个请求，都携带一份看不见的载荷。你的 tool schemas、system prompt、skills 目录、功能指令，全都打包在一起发送——而每一个 token、每一轮，你都在为此买单。

在你敲下第一个字之前，账单就已经不小了。

问题出在可见性上。/context 命令会把你的 window 按类别拆开，但它把所有 tools 归并成了一个数字。你看得见总量，却看不出哪个具体的 tool 吃掉的 token 最多。要精准下刀，你得看到真实的载荷。

配置 request logger（Set Up The Request Logger）

你的目标是：检查每次发给 agent provider 的请求中实际发送了什么，然后找出并砍掉其中最大的几个元凶。

  • 启动 request logger

在一个终端里运行 request logger：

npm run request-logger

它会询问你用的是哪个 coding agent；如果你的 agent 能用多个 model provider，还会问你是哪一个。它能记住你的答案，所以只需要问一次。然后它会在 "Run your agent in another terminal with:" 这一行下方，打印出专属于你的 agent 的确切命令。

  • 把你的 agent 指向这个 logger

把那条命令复制粘贴到一个新终端里运行。它是为你选的 agent 量身打造的，不需要做任何调整。如果你的 agent 还需要一个配置文件，logger 会在命令上方把它打印出来。

  • 清掉旧日志

删除 request-logger/logs/ 里的所有文件，让自己从零开始。

  • 发一条测试消息

在你的 agent 里发送一条简单的消息：

Hello!

等它回复。然后查看 request-logger/logs/——现在你应该会看到一个新日志文件（一份 .md 渲染版，外加 .request.txt 和 .response.txt 文件）。

VS Code 中显示的 request-logger/logs/ 目录及新生成的日志文件

检查载荷结构（Examine The Payload Structure）

现在打开日志文件，探究每次请求都发送了什么。

  • 搜索并阅读 system prompt

在日志文件里搜索 <system-prompt>。花点时间弄清楚里面都有些什么。

请特别注意：- Environment 部分——它告诉 agent 你的操作系统、shell 和工作目录 - Context management 部分——agent 如何处理长对话 - 最近的 git 提交记录（如果你用的是 Claude Code 这类 agent）

  • 查看所有可用的 tools

找到 <tools> 部分。你的 agent 可用的每一个 tool 在这里都有自己的定义。

往下滚动时，留意：- 一共列出了多少个 tools（你很可能会看到 70 多个定义）- 哪些 tools 你真的听说过（Artifact、Bash 等）- 哪些 tools 你完全陌生——去读它们的描述。有些会相当冷门：CronCreate、DesignSync、EnterPlanMode、Workflow - 有些定义体量有多大——里面有大段冗余文字，在解释 commit message 格式、PR 模板和 feature flags

  • 找出 MCP tools

在文件里搜索 mcp__。这些是通过集成挂载上来的 Model Context Protocol tools。

你会看到这样的 tools：- mcp__claude_ai_Figma__authenticate - mcp__claude_ai_Gmail__create_draft - mcp__claude_ai_Slack__authenticate - mcp__claude_ai_Google_Drive__search_files

数一数这样的 tool 一共有多少。无论你需不需要，这些 tools 都会随每一个请求一起发送。

  • 查看 skills 列表

搜索 "following skills are available"，找到 skills 目录。你会看到一份包含 15 到 20 多个 skills 的清单，每个都带描述。

留意哪些是项目特有的，哪些是你的 agent 默认内置的。

理解成本（Understand The Cost）

  • 在你的 agent 里运行 /context

看看你的系统在不同类别（system prompt、tools、skills、messages）上各用了多少 token。

仅仅一条 "Hello!" 消息，request logger 完整的 markdown 渲染通常就有 4,000 多行、150 到 200 KB。这整份载荷每一轮都会被发送、被计费。

现在你明白了每个请求背后那笔看不见的成本。解决方案视频会教你如何把它砍下来。

消灭 bloat：解决方案（Killing Bloat Solution）

第一步，在你的 ~/.claude 目录里创建一个 settings.json 文件，并把它初始化为一个空对象。

这里演示的步骤是针对特定 agent 的，但如果你看下面的文字版课程，那里同样有按需清除 bloat 的 harness 操作指引。

操作流程（The workflow）

每次修改 settings.json 之后，流程都一样：

  1. 编辑 ~/.claude/settings.json
  2. 退出你的 agent
  3. 重新启动它
  4. 发送一条 Hello! 消息
  5. 运行 /context 命令
  6. 查看日志，看有什么变化

为了给我们一个基线参照，先在全新启动的状态下跑一次 /context。我们的起点是 68.3k token。这可真不少。

禁用 MCP connectors（Disable MCP connectors）

首先要处理的是 MCP（Model Context Protocol）相关的东西。只要你用 Claude.ai，就会有一堆 Claude AI connectors 自动启用。

在 ~/.claude/settings.json 里，你可以一次性把它们全部禁用：

{
"disableClaudeAiConnectors": true
}

重启并运行 /context 之后，我们已经降到了 47k token。一个设置就省下了 21k token。

禁用 workflows（Disable workflows）

接下来你会注意到，有大量与 dynamic workflows 相关的配置。它们以确定性的方式编排多个 sub-agent。

如果你不打算用 workflows，就禁用它们：

{
"disableClaudeAiConnectors": true,
"disableWorkflows": true
}

现在降到了 39k token。

禁用内置 skills（Disable bundled skills）

内置 skills 包括 deep research、data visualization、artifact design、config updates 和 keybindings help。如果你一个都不用，就把它们全禁掉：

{
"disableClaudeAiConnectors": true,
"disableWorkflows": true,
"disableBundledSkills": true
}

这一步把我们降到 37.1k token——同时也彻底关掉了 skills 的使用。

禁用 artifacts（Disable artifacts）

有个比较新的功能叫 Artifacts，你可能完全用不上。关掉它很简单：

{
"disableClaudeAiConnectors": true,
"disableWorkflows": true,
"disableBundledSkills": true,
"disableArtifact": true
}

又少了 4k token，现在到了 33.1k token。

用 permissions 控制 tool 访问（Control tool access with permissions）

现在来处理大头：审视 tool 定义本身。

**关键原则在这里：如果你通过 permissions.deny 拒绝 agent 访问某个 tool，它的定义就会从 system prompt 中被整体移除。**这不只是运行时的拦截——这是在每一次请求上都省下 context。

我们来看看你真正需要哪些 tools：

Tool 问问自己…… 操作
NotebookEdit 你需要在 Jupyter notebook 中替换、插入或删除单元格吗？ 多半不需要。禁掉。
DesignSync 你需要设计、同步、读取和更新 Claude.ai 的 design-system 项目吗？ 不需要。禁掉。
CronCreate、CronDelete、CronList 你需要创建和管理 cron 任务吗？ 多半不需要。三个都禁掉。
EnterPlanMode、ExitPlanMode 你需要 agent 进入和退出 plan mode 吗？ 不需要。两个都禁掉。
PushNotification、RemoteTrigger 你需要推送通知或远程触发吗？ 不需要。两个都禁掉。
ReportFindings 你需要 agent 汇报发现吗？ 不需要。禁掉。
ScheduleWakeup 你需要唤醒调度吗？ 不需要。禁掉。

把这些加进你的 settings：

{
"permissions": {
"deny": [
"NotebookEdit",
"DesignSync",
"CronCreate",
"CronDelete",
"CronList",
"EnterPlanMode",
"ExitPlanMode",
"PushNotification",
"RemoteTrigger",
"ReportFindings",
"ScheduleWakeup"
]
},
"disableClaudeAiConnectors": true,
"disableWorkflows": true,
"disableBundledSkills": true,
"disableArtifact": true
}

这一步把我们降到了大约 21.6k token。

还有一个 tool 值得禁用：AskUserQuestion。它的 tool 定义非常长（约 130 行），有人很喜欢它的 UI，也有人觉得它碍事。

把它移除后，我们降到了 20k token 以下——大约 19.9k。这是个不错的收尾点。

态度比细节更重要（The attitude matters more than the specifics）

这个演示是针对特定 agent 的，但真正重要的是这种态度。

你必须清楚自己 system prompt 里发送的所有 token。你不必逐字读完，但必须留意是不是混进了不该在的东西——因为它会影响之后的每一次请求。

对自己的 tools 和配置做这种清洁工作非常重要。注意，我们在这里移除的所有东西，本来就是你不会用到的。它们绝对不该待在那里，影响行为、吞噬宝贵的 token。

代码库探索（Codebase Exploration）

每当 agent 面对你的 codebase 开启一个全新 session，它都必须通过探索来找到自己需要的信息。stateless（无状态）是最难绕开的约束——agent 对之前的 session 毫无记忆。

agent 探索的质量，直接决定了接下来一切的质量。如果它找不到需要的信息，多半就做不成你想做的事。

所以探索这件事很重要，非常重要。而让你的 codebase 易于探索，是你能做的最重要的事情之一。

agent 已经知道什么（What The Agent Already Knows）

当你启动一个 session 时，agent 会自动拿到一些环境信息。我们来看看都包括什么：

  • 平台（Linux、macOS、Windows）
  • 工作目录（所以它能从仓库名里猜出点什么）
  • Git 仓库状态（分支、主分支、git 用户、最近的提交）
  • shell 类型（bash、zsh 等）
  • 你的助手的知识截止日期

这些其实相当有用。但存在一个关键的缺口。

agent 不知道什么（What The Agent Doesn't Know）

agent 完全拿不到任何文件系统信息。它没有当前目录的 ls 结果，没有文件树，对目录里实际存在哪些文件一无所知。

所以 agent 知道的只有：

  • 目录名
  • 它所处的大致环境
  • 一些最近的提交名
  • 对真实文件系统则一无所知

这恰恰就是你此刻作为这个仓库学习者的处境。你对我们要构建的这个应用大概还知之甚少。你和你的 agent 正处在相似的位置上。

这个模式为什么有效（Why this pattern works）

在大型仓库里，大多数时候 sub-agent 就是这样工作的：

  1. sub-agent 读取一堆文件
  2. 它把所有这些信息整合起来
  3. 它向父 agent 汇报一份总结，其中包括关键文件路径和大量细节

父 agent（即 orchestrator，编排者）保持精简，而 sub-agent 们则把 token 花在深度探索和总结发现上。

选择你的探索策略（Choosing your exploration strategy）

很多人更喜欢让 sub-agent 出去执行探索。这样，orchestrator 里的 context window 就能保持得非常紧凑。

这正是「留意你的起始 context window」带来回报的地方。如果你的起始 context 很大，那么每次开启一个 sub-agent，你都要付出这份代价。让它保持小巧意味着更经济，你在 smart zone（聪明区）里待的时间也更长。

所以，为什么探索如此重要、为什么用 sub-agent 做探索如此有效，现在就说得通了：它让你在把 token 成本控制在合理范围内的同时，还能扩展自己对大型代码库的理解。

关键难点：同一个组件，两台机器（The tricky bit: Same component, two machines）

课程里有一个重要的提示框。在第 3 步和第 5 步，同一个组件函数运行了两次——一次在服务器上，一次在浏览器里。相比之下，loader 只在服务器上运行，而且每一次都是如此。

这种不对称正是你需要理解的核心概念。

当课程向你展示真实文件时，它剥掉了无关的一切，只留下要紧的部分：

// app/routes/courses.tsx

export const loader = async (args: LoaderFunctionArgs) => {
// ...
};

export default function CourseCatalog() {
// ...
}

export const ErrorBoundary = () => {
// ...
}

export const meta = () => {
// ...
}

这些导出名——loader、default、ErrorBoundary、meta——是一份契约。React Router 按照确切的名字查找它们。把 loader 改名成 fetchData 会弄坏一切。

  • app/routes.ts 文件里列着它
  1. 默认导出的组件运行几次？
  • 两次：先服务器，后浏览器
  1. 路由的 loader 函数实际在哪里执行？
  • 只在服务器上，每次都是
  1. 在路由文件里把 loader 改名为 fetchData 会……
  • 弄坏它：这个名字是一份契约
  1. 搜索课程是通过什么方式过滤列表的？

// components can import them without pulling the database driver into the
// browser bundle.

export const MIN_RATING = 1;
export const MAX_RATING = 5;

现在 star-rating.tsx 改为从 app/lib/ratings.ts 导入，而不是从 service 导入。组件拿到了它需要的东西，却不会触发一整条依赖链。

为什么 plan mode 很糟糕（Why Plan Mode Sucks）

在上一课里，我们看到了 agent 在常规条件下的表现。结果并不理想。真正让我不安的是那个模式：一条提示词进去，agent 探索了代码库，随即就开始实现。

它没有和我们核实自己要造的东西对不对。AI 与我们之间也没有任何建立对齐的尝试。

那一轮我们其实算是走运。agent 把我们想要的东西做得相当不错。有一些小问题和关键的 bug，但总之能用。然而，这种急于产出成品的冲劲在 AI 编码里非常危险，也是我一直努力踩刹车的地方。

plan mode：探索与实现之间的缓冲区（Plan mode: a buffer between exploration and implementation）

大多数 agent 都自带一个叫 plan mode（计划模式） 的东西。plan mode 的本意是在任何工作开始之前，先进行一轮规划 session。这轮规划 session 会产出一份计划文档，你阅读、审阅，然后决定是否继续（也可以带着修改继续）。只有当你对计划满意了，才往下走。

让我给你演示这在实践中是怎么运作的。

这会把代码库重置回 main 分支，并清掉上一课里已有的课程评分实现。

接着，我会打开 agent，用 shift+tab 在各个 permission mode（权限模式）之间循环切换，直到输入框底部显示 "plan mode on"，以此启用 plan mode。

These reviews will then be visible everywhere that courses are visible. We want to show the average rating on the courses in the list page and on the course page itself.

提交之后，agent 应该会先探索代码库来理解结构，然后带着一份计划回来。这个 plan mode 就像是探索与实现之间的一个小缓冲——一个让我们在继续之前先对齐的时刻。

关键问题：plan mode 依然在赶（The critical issue: plan mode is still rushing）

问题在这里：agent 没有急着产出实现，而是急着产出了一份计划——而这份计划读起来跟实现方案一模一样。

它已经把即将执行的实现原封不动地端给了我：

  • 数据库表结构
  • Service 的命名与函数
  • 组件命名
  • 路由改动
  • 测试策略

它依然在急着产出一件成品。只不过现在这件成品是计划，不再是代码。

根源：agent 的 sycophancy 特性（The root cause: sycophantic trait of agents）

这种「提前宣布完成」的感觉、这种一路冲向终点的急躁，是 agent 的 sycophancy（谄媚）特性。当你告诉它你要产出一个东西，它就会径直去把那样东西生产出来。

它未必会停下来确认：自己是否已经做足了前期功课，确保你们就「它应该长什么样」达成了一致。

这真的很糟，因为它会导致一个反复出现的失败模式：agent 造出了错误的东西。

对课程评分这种相对简单的功能来说，影响还不算大。但换成更复杂的功能，这就真的非常要紧了。

这在实践中意味着什么（What this means in practice）

想象一下，如果一个人类开发者也这样行事。他只丢下一句「会，我知道怎么造」，然后就直接动手了。这将不存在任何对齐，也完全感受不到一种共享理解正在逐步形成。

Frederick P. Brooks Jr.（《The Mythical Man-Month》的作者）在《The Design of Design》这本书里提出了一个概念，叫 design concept（设计共识）。

design concept 不是一件成品。它是人们一起设计某样东西时，飘荡在房间里的那个概念。每个人对它的想象都略有不同，但随着对话推进、随着你们一起努力搞清楚要造的是什么，一切开始变得清晰、锐利。

无论在 plan mode 里，还是在我们前面看到的那种做法里，都不存在 design concept。没有一个时刻让彼此停下来核对：我们是否真的就「在造什么」达成了一致。

第一次跑的时候我们拿到了一个还过得去的结果，但我敢保证，换成更复杂的功能，这很快就会出岔子。

另一种方法（A different approach）

我设计的方法试图绕开这个问题。它移除了那种谄媚式的成品冲刺。我希望你最终收获的，是一种与 agent 对齐感更强的体验——就像你们俩读的是同一页剧本。

我会在下一课讲解这个方法。

随堂测 · Quiz

你在 plan mode 下提交了一个功能请求。agent 探索之后交回一份计划，上面写明了数据库表、service 函数、组件和测试策略。这有什么问题？

  • 它又一次急着产出成品——这份计划就是实现
  • 它太模糊，没法审阅，你无法判断这个方案
  • 它跳过了对代码库的探索，所以这份计划是瞎猜的
  • 它无法修改，你只能原样接受这份计划

答案与解析

你说出你想要的东西，agent 就去把它生产出来，从不停下来确认你们对它该长什么样看法一致。这是 agent 的哪种特性？

  • Sycophancy——你要什么就产出什么
  • Hallucination——凭空编造毫无来源的事实
  • Non-determinism——每次运行表现都不同
  • Degradation——session 越长越失焦

答案与解析

你和一位同事把一个功能从头聊到尾，直到你们俩脑中的画面完全一致，而且什么都没写下来。你们拥有的是什么？

  • 一个 design concept——共享的理解，而不是一件成品
  • 一份可以用来对照检查实现的规格说明
  • 一份计划文档，只不过以非正式的口头形式存在
  • 在你们其中一人把决策写下来之前，什么可用的东西都没有

# Grill-Execute-Clear 循环（The Grill-Execute-Clear Loop）

Commit Map（提交对照）

grill-me-skill 本课起点：.agents/skills/ 中新增的 /grill-me skill

lesson-comments 查看我的解法：基于 grilling 得出的 spec 构建的课程评论功能

在开始构建功能之前，你得先弄明白自己要构建的究竟是什么。大多数开发者会跳过这一步，一头扎进代码里，结果往往是白白浪费时间，做出来的方案也不太贴合问题本身。

/grill-me skill 会强迫你停下来。它会毫不留情地「面试」你，直到你们对要构建的东西达成共享理解为止。只有到那时才开始实现。

这就是 grill-execute-clear 循环：先 grill 到理解透彻，再 execute 出解决方案，然后 clear 掉脑中的负担，转向下一个功能。

grilling 技能（The Grilling Skill）

grilling skill 的工作原理是构建一棵 design tree（设计树）。每个决策都会分叉出挂在其下的其他决策。

它按轮次提问。所谓 frontier（边界），指的是所有前置条件均已敲定的那些决策。skill 会一次性把整个 frontier 上的问题全部抛出，然后等待你的回答。

随着你作答，frontier 不断扩张。新的问题被解锁，先前被阻塞的决策变得可以回答。

当 frontier 清空时，session 便告结束：每条分支都被访问过，没有任何东西被悄悄假设。只有在这之后，你才应该动手实现。

你的任务（Your Task）

为课程平台构建课程评论功能。学生和讲师应该能在单个课程页面上发表评论。

想象一下你浏览到「Connecting to a Database」或「CRUD Operations」这样的课程页面。在这个页面上，学生应该能提问、分享心得，并与其他学生和讲师讨论课程内容。

这个练习刻意保持开放，就像之前课程星级评分的练习一样。但这一次，你不再急着实现，而是先用 /grill-me 去探索这个功能的空间。

skill 会问你这样的问题：

  • 谁能评论？只有已选课的学生？讲师也可以吗？
  • 用户能编辑或删除自己的评论吗？
  • 评论应该做成嵌套串（threaded），还是平铺（flat）？
  • 评论需要审核（moderation）吗？
  • 有人回复时，用户应该收到通知吗？

这些问题你未必全想过。而这正是意义所在。grilling 过程会在你写下任何代码之前，把需要做的决策统统摆上台面。

第一轮：战略性问题（Round 1: The Strategic Questions）

This is for other teachers.
I think the expectation of a response should be there.
I think I would prefer to build it.

Compaction 压缩（Compaction）

用 agent 构建功能时，你迟早会抵达 smart zone（聪明区）的尽头——也就是 context window 中 model 表现最好的那一段。接下来会发生什么？

如果你继续待在同一个 session 里，结果会慢慢劣化。agent 每次请求都会把之前所有的 token 一并送上。这些 token 因为已被缓存而更便宜，但你仍在一个延迟更高、能力更弱的环境里工作。

更关键的问题是：这些 token 里到底有多少真正有用？其中一大块只是干活过程本身产生的噪音——读文件、写文件，以及项目推进途中处于各种中间状态的文件。

天真的解法：从零开始（The Naive Solution: Starting Fresh）

一个选项是彻底清空 context，开一个新 session。但这有一个隐性代价。

清空 context 后，agent 会丢失最初对话中至关重要的理解。它必须重新探索、重新建立起之前知道的一切。你可能会这样提示它：

we are going to do QA on the stuff that's literally just been worked on.
Can you go and explore it so you understand the reasons behind its existence?

agent 会去做那番探索，但它已经丢掉了你们最初对话里的一些关键推理。

它可以重新探索代码、重读你构建的东西，但这种重新探索是有损的——你当初为什么这么建，那份真实的 why 已经丢掉了大半。

初识 Compaction（Introducing Compaction）

这正是 compaction（压缩）登场的地方。compaction 不把 context 整个清掉，而是取当前 session 的 context，把它挤压浓缩，再用它去 seed（播种）一个全新的 session。

你可以把它想成一次由你掌控的、session 与 session 之间的 handoff——类似使用 subagent（子智能体），只是方向相反。session 历史被总结成摘要，然后作为种子生成一个你可以继续工作的全新 session。

方案 Tokens 质量 缺点
继续当前 session 156k+ 完整 context，噪音很多 高延迟，dumb zone 结果
清空重来 ~5k 一张白纸 一切都要重新探索，理解有损
Compaction ~28k 摘要化的 context 有损压缩，二手来源

Compaction 省掉了重新探索。没有它，你得烧掉大量 token，只为重新发现那些你早就建立好的 context。

代价：信息损失（The Trade-off: Information Loss）

Compaction 并非没有缺点。不妨借用历史学的术语来理解它：

把 compaction 摘要比作俯瞰整个 session 的「历史学家」

  • **primary source（一手来源）**是你的初始 session——当时在场者留下的记录
  • **secondary source（二手来源）**是摘要——一份历史总结，是对一手来源的有损压缩

Compaction 是你见到的第一种能在 session 之间保留 context 的 handoff 机制。但所有 handoff 机制都有同一个毛病：只要创建二手来源，就会丢失信息。

不过，你换来的是效率。这笔交易是这样的：

方案 信息 噪音 机动空间
一手来源（继续） 完整 很多 受限
二手来源（compaction） 有损 更少 更充裕

如果你继续用一手来源，你拥有全部信息，但多半还附赠大量噪音。如果你用二手来源，你有更多回旋余地、占用空间更少，但可能会丢失一手来源里的某些细微之处。

Compaction 的高光时刻（When Compaction Shines）

不过，在你刚完成一项工作、正想对它做 QA 的这种确切场景里，compaction 是板上钉钉的绝佳用武之地。你不是在重新实现，不是在做架构决策，你是在验证一件已经完成的东西。

这里只是 compaction 的入门。在接下来的课程里，你会看到它与 clearing 以及其他机制的比较。

# Handoff 交接（Handing Off）

Commit Map（提交对照）

handoff-skill 本课起点：.agents/skills/ 中新增的 /handoff skill

在上一个练习里，我给你演示了 compaction 是怎么工作的：取一个 session 的 primary source（一手来源），把它总结成 secondary source（二手来源），再用它去 seed 一个新 session。

不过，compaction 有一些限制。它只能在同一个目录里压缩，也只能在同一个 agent 里压缩。

举例来说，如果我们用 Claude 做了一些实现，想把它 handoff 给另一个 AI agent（比如 Codex）去审查，用 compaction 该怎么做到？做不到。

/handoff skill（The /handoff skill）

  • 喂给 Codex
  • 传给另一个目录里的 agent
  • 发给一位同事
  • 用来交接你在功能开发途中发现的某个支线任务

一个特别好用的场景是：你正在做一个功能，注意到一个与你正在构建的东西无关的随机 bug，想以后在单独的 session 里修掉它。你只需创建一个 handoff artifact（交接产物），回头再来处理。

# Clear、Compact、Handoff 还是 Subagent（Clear, Compact, Handoff, Or Subagent）

在我们目前用 agent 做过的那些编码 session 里，你可能已经注意到，它们会切分成相当离散的几块。我们经历过一个 grilling 阶段，然后一个实现阶段，最后还有一个 QA 阶段。我们在开始 QA 之前做了 compaction。

这些阶段的界定比较宽松。它们其实就是一个编码 session 里的几块工作。每个阶段都由两部分组成：阶段本身（运行 grilling、实现或 QA 的那段过程），以及它们之间的边界。

边界极其重要。它们代表一个决策点：在每条阶段边界上，你都要决定拿这个 session 怎么办。

展示我们分配给每条阶段边界的选择

但实现结束、想要 QA 时，我们决定 compact。可以说，我们的 smart zone 已经用得差不多了，我们想丢掉所有杂质，只把好东西留给 QA。

怎么做出这些决定，并不是特别显然。在这些阶段边界上，你其实有五个选项。

你的五个选项（Your Five Options）

选项 作用
Continue（继续） 留在当前 session，无需切换 context
Clear（清空） 彻底清空 context window，从零开始
Compact（压缩） 压缩 context，用它 seed 一个新 session
Handoff（交接） 生成一份总结该 session 的 markdown 文件，可传到任何地方
Subagent（子智能体） 派生一个 subagent 处理任务并汇报结果

把这五个选项用得得心应手绝非易事。我做了一棵决策树帮你理清它们。第一眼看上去可能挺吓人，但我们会一步一步走完它。

决策树：从顶端开始（The Decision Tree: Start At The Top）

当你走到一个阶段的尽头、不太确定该干什么时，就从这里开始。

问题 1：你能继续吗？（Question 1: Can You Continue?）

继续待在当前 session 里是否说得通？

这本身就是个内涵相当丰富的决策。在 grilling 和实现之间，继续显然说得通：我们手里握着需要的那份丰富一手来源，到了实现阶段可不想把它丢掉。

如果 smart zone 预算还够，你也可能想继续。比如你在 80k tokens 左右，知道接下来的任务很小、完全装得进 smart zone，那就继续好了。

如果你认定确实需要做点什么，那就要进入这棵小决策树了。

决策树第一个问题：你能继续吗？

问题 2：你的 context 对下一个任务无关紧要吗？（Question 2: Is Your Context Irrelevant To The Next Task?）

如果你需要做点什么，先问自己：这个 session 里的全部信息是不是完全可以丢弃？

换句话说，这个 session 里的探索、做过的决策——对于接下来要做的事，是不是完全无关？

如果是，清空你的 context window。 只要走得通，clearing 就是效率最高的路径，因为它耗时为零。你只是在删除信息，然后你就拥有了最多的 smart zone。你回到了一张白纸。

然而，如果你在 context 里还装着相关信息时就把它清掉，你丢失的可能是日后有用的东西。想象一下，如果我去做 QA 时选择了 clear 而不是 compact。这意味着 QA 对实现一无所知——这也许还能接受，它可以从 git commit 里琢磨出来。但它同时也会丢掉 grilling 阶段的全部信息。

它会丢掉我做出那些决策背后的推理。这两个阶段对随后的 QA 都很重要。所以 clearing 根本不是一个选项。

如果否，你的 context 是相关的。 进入下一个问题。

决策树第二个问题：你的 context 无关紧要吗？

问题 3：你需要 handoff 吗？（Question 3: Do You Need To Hand Off?）

这一条专门针对 handoff skill。和其他选项相比，handoff skill 的适用面相对窄。

只有当你需要：

  • 把工作交给另一个 agent
  • 把工作交给另一个目录或另一位同事
  • 把阶段途中发现的支线任务分叉出去，而不让当前 session 脱轨

时，才需要做 handoff。

比如，你可能在做 grilling 的过程中发现某件同样需要处理的事。你可以在继续手头工作的同时，把它 handoff 给另一个 session。

如果是，使用 handoff（/handoff）。如果否，进入下一个问题。

决策树第三个问题：你需要 handoff 吗？

问题 4：这个任务能 AFK 完成吗？（Question 4: Can The Task Be Done AFK?）

AFK 的意思是 away from keyboard（离开键盘）。 你不碰键盘，只是看着 agent 干活，而且无法干预。

这意味着任务的范围已被圈定得很清楚。agent 不需要你的任何干预就能完成。

假设我们想在 human review（人工审查）介入之前，先对实现做一次 automated review（自动化审查）。automated review 就是把 agent 放进代码库，让它查看改动，检查有没有弄坏什么、有没有做出什么怪事。

以 automated review 作为 AFK 任务示例的图示

我们本可以在此时 compact（实现之后我们已到 150k tokens），然后在主 session 里跑审查。但既然 automated review 不需要人，那不如放到 subagent 里跑。这样它就在自己的 context window 里运行，完全不影响主 session。

这是 automated review 非常见用的模式，本课程后面也会讲到它。

如果是，派生一个 subagent。 如果否，进入最后一个选项。

决策树第四个问题：这个任务能 AFK 完成吗？

默认选项：Compact（The Default: Compact）

这是决策树的底部。当你的 context 是相关的、你想拿这个 context 做点什么、你不能继续、你不需要 handoff、而且这个任务需要你在场才能做——那么 compact 就是答案。

Compact 压缩你的 context window，把好东西 seed 进一个新 session。你留下要紧的，丢掉不要紧的。

这些都是主观决策（These Are Subjective Decisions）

这些问题并不客观。里面有一点主观，一点品味。随着你继续工作、继续与 agent 相处，你会找到属于自己的答案。

但我希望「阶段」这个概念、以及在阶段边界上该做什么这件事，能真正刻进你脑子里。这是 AI 编码时你要做的最模糊、也最有意思的决策之一。它需要大量讨论，也需要大量智慧。

# Auto-Compaction 自动压缩（Auto-Compaction）

你可能会好奇：如果你试图冲破 context window 的上限，会发生什么？我们用的 Opus 4.8 有 100 万 token 的 context。如果你冲到 100 万零 1，会怎样？

如果你发给 Anthropic 的请求里有 1,000,001 个 token，你会收到一个错误。model 就是无法处理那么多 token。

你的 agent 内置了防止撞上这条硬上限的保护。到达某个点时，它会自动 compact 你的 session。

在你的 agent 里找到 Auto-Compact（Finding Auto-Compact in Your Agent）

你可以在 agent 里输入 /config 命令，然后搜索 auto-compact，就能看到这个设置。匹配的设置会出现在顶部。

/config 面板显示 Auto-compact 设为 true

相关配置显示为：

Auto-compact: true

附带说明：「Automatically compact conversation when context fills」（context 填满时自动压缩对话）。

每一个 agent harness 里都有 auto-compaction，因为每个 harness 都有这个问题。每个 harness 都有一个窗口阈值，一旦触及，系统就会暂停你的 session，并自动压缩其中的内容。

以前你可以输入 /context，在 context 明细里看到 autocompact 的 buffer（缓冲区）。但看起来各家团队已经把它弄得没那么容易看到了。

自定义 Auto-Compact 窗口（Customizing the Auto-Compact Window）

有一件有趣的事你可以做：自定义 auto-compact 窗口本身。在你的 ~/.claude/settings.json 文件里，你可以调整 auto-compaction 何时触发：

settings.json 文件显示 autoCompactWindow 设置

{
"autoCompactWindow": 250000
}

如果你想让它在 250,000 tokens 之后自动 compact，完全可以。这个设置接受从 100,000 到 1,000,000 tokens 之间的值。

承诺：context 管理从此消失（The Promise: Context Management Goes Away）

Auto-compaction 的愿景听起来非常美好。想象一个你完全不用思考阶段边界、不用思考 smart zone、完全不用思考 context 的世界。

这棵决策树将根本不再需要：

展示全部五个选项的决策树图

  • 继续 session
  • 清空 session
  • 把它 handoff 出去
  • 派生一个 subagent
  • Compact

你只会在恰当的时机自动 compact。事实上，你会在网上看到很多人说，auto-compaction 替他们搞定了一切问题。

为什么 Auto-Compaction 其实非常难（Why Auto-Compaction Is Actually Really Difficult）

然而事实证明，auto-compaction 是一个极难解决的问题。而且做错了会非常非常疼。

在阶段中途 compact 很危险（Compacting in the Middle of a Phase Is Dangerous）

回想一下一个典型 session：一个 grilling 阶段加一个实现阶段，中间隔着一条阶段边界。

展示 grilling 阶段、实现阶段与阶段边界的图示

如果有人强迫你在这个 session 的某处塞进一次 compact，你多半会说，最安全的位置是阶段边界上，也就是 grilling 和实现之间。

但如果在 grilling session 的中途 compact 会怎样？你将只拿着「之前做了什么」的一份摘要来工作。当这种事偶尔发生时，我发现 agent 确实经常彻底迷路，把你刚刚还在聊的东西忘得一干二净。

实现阶段同理，而且往往更糟：

  • agent 会经常完全迷失方向
  • 实现阶段的后半部分会用一种与前面完全不同的编码风格
  • 它会丢失思路，忘记本该实现的功能

你失去了对 handoff 的控制（You Lose Control of the Handoff）

还有一个问题：自动 compact 时，你没有机会说明该压缩什么、下一个 session 的意图是什么。

你传给 handoff 文档或 /compact 的那些小小的总结性提示，是让它压缩对的东西的关键。Auto-compaction 没有给你任何等价的钩子。

更好的方式：由人掌控（The Better Approach: Human Control）

那么，阶段中途的 compact 就永远都不好吗？倒也未必，尽管无论 model 有多强，这看起来都会是个难题。这是个非常棘手、非常难解的问题。

我的总体态度是：提升人的技能，而不是提高对 harness 和 model 的要求。我倾向于让这个人来掌控这棵决策树，而不是把它整个甩给 agent。

这是人要经历的一次性学习曲线，而且你越熟练，结果就越好。你的 session 会有更多停留在 smart zone 里，你的掌控力也会更强。

真正的规则（The Real Rule）

在我看来，如果你撞上了 auto-compact buffer，如果你的 session 在自动压缩，那么多半说明有什么地方出了问题。

相反，你应该掌控局面。继续 session、清空 session、把它 handoff 出去、派生一个 subagent 还是 compact——应该由你来决定。

当你拥有这个决策权，你就能得到更好的代码。
