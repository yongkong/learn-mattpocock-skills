如何应对巨型任务（How to Tackle Massive Tasks）

希望你已经染上了我的 context window（上下文窗口）妄想症。看得出来，我无时无刻不在惦记 context，惦记 smart zone 和 dumb zone。

呆在聪明区里（Staying in the Smart Zone）

以当前这代 model 而论，我主张待在 context window 的前段，也就是 smart zone（聪明区）里。

对于只需要在单个 context window 内完成的任务，这样完全够用。比如小功能或 bug 修复，从头到尾一个 session 搞定。

任务 #1 和 #2 完全落在 smart zone 内

当任务装不下的时候（When Tasks Don't Fit）

可当你想做点更大的事——注定要闯进 dumb zone（愚蠢区）的事，比如一次触及应用每一层的重构——会发生什么？

或者一眼就能看出连单个 context window 都装不下、更别提 smart zone 的任务呢？

任务 #3 溢出进 dumb zone，任务 #4 撑爆了整个 context window

换句话说，怎么把一大坨工作一口气交付出去？

拆解问题（Breaking Down the Problem）

答案是用开发者们用了几十年的老办法：把大任务拆成小块，每一块都能装进 agent 的 smart zone。

任务 #4 被拆进四个 smart zone 格子

那么问题就变成了：要让这一切跑通，你需要做怎样的前置规划？毕竟到目前为止，我们的计划其实只够撑过单个 context window 的时长。

我们还从没认真想过，让 agent 跨多个 session 工作、让一项工作横跨多个 context window，会是什么样子。

两份必不可少的文档（Two Essential Documents）

我在这个问题上做了大量实验，试过很多不同的路子，最后落到一个方案上：它依赖两份文档。

1. spec（The Spec）

spec 的定义：一份描述多 session 工作目的地的 handoff artifact

我们需要的第一份文档，是对目的地的描述——我们要去的地方。因为连要去哪都不知道，又怎么完成任务？又怎么知道自己做对了？

我称这份目的地文档为 spec（规格），一份描述多 session 工作之最终目的地的 handoff artifact（交接产物）。

这份 spec 会传给每一个 session，让每个 session 都知道自己的工作是如何贡献于最终目标的。

最后我们还会拿这份 spec 来做审查，确保我们真的到达了当初声称要去的地方。

2. tickets（Tickets）

但这里有个问题。如果 spec 里只写了目的地，agent 怎么知道该把它拆成哪些小块？除了目的地，我们还得把旅程也描述清楚。

tickets 的定义：spec 和 tickets 都是 handoff artifact

这正是为什么除了 spec，你还要写 tickets：每份要装进一个 smart zone 的工作对应一张 ticket。按图里的情况，就是四张 ticket。

每张 ticket 描述那个 session 里要做的事，所以它就是这份 spec 的实施计划。

承接有野心的工程（Scaling Ambitious Work）

有了这套打法，你敢接的活可以非常有野心。我手头就有过带着 30 张 ticket 的巨型 spec，最后结果也不赖。

这就是本节的主旨。我们要聊的，是如何用 specs 和 tickets 交付比以往你能想象的更大、更有野心的项目。

答案与解析

spec 和 ticket 的区别是什么？

  • spec 是目的地；每张 ticket 是旅程中的一段
  • spec 是长版本；ticket 是同一份计划的精简版
  • spec 在 tickets 之后写，用来记录建成了什么
  • spec 是写给你看的；tickets 是写给 agent 看的

spec 模板（The Spec Template）

生成的 spec 用的是一个相当扎实的模板，包含：

  • 问题陈述（problem statement）
  • 解决方案描述（solution）
  • 一大把 user stories（用户故事，经典软件开发手法）
  • 实现决策（implementation decisions）
  • 测试决策（testing decisions）
  • 范围外条目（out of scope）
  • 补充说明（further notes）
## Problem Statement

The problem that the user is facing, from the user's perspective.

## Solution

The solution to the problem, from the user's perspective.

## User Stories

A LONG, numbered list of user stories. Each user story should be in the format of:

1. As an <actor>, I want a <feature>, so that <benefit>

## Implementation Decisions

A list of implementation decisions that were made. This can include:

- The modules that will be built/modified
- The interfaces of those modules that will be modified
- Technical clarifications from the developer
- Architectural decisions
- Schema changes
- API contracts
- Specific interactions

Do NOT include specific file paths or code snippets. They may end up being outdated very quickly.

## Testing Decisions

A list of testing decisions that were made.

## Out of Scope

A description of the things that are out of scope for this spec.

## Further Notes

Any further notes about the feature.

这些内容足够丰富，任何接手它的东西——也就是负责实现的 agent——都能获得一次非常给力的信息注入，顺利完成实现。

但拆分工作有好方法，也有坏方法。

横切是一个陷阱（Horizontal Slices Are a Trap）

每个应用都有分层。你可能有一个数据库、一个 API 和一个前端，各自作为独立的部署单元。应用内部，你可能有负责与前端通信的 service；前端内部，又有自带层级的组件。

展示应用分层的示意图：数据库、API、前端、service 与组件

当 agent 面对涉及不同层级的工作拆分时，它通常会切成水平切片（horizontal slices），让每个层级各自领到一个阶段。

阶段 1 专注数据库。阶段 2 把它接到 service 上。阶段 3 再把所有东西接到前端。

展示水平切片的示意图：每个层级各自一个阶段

这看起来井井有条、合情合理，但其实是个陷阱。软件开发者们几十年前就明白这一点了。

如果按这种方式做，阶段 1 写下的所有代码，你要等到实现阶段 3 时才能真正知道它能不能跑、设计得好不好。你必须跨过所有层级，才能判断某一层的代码设计是否合理。

用水平切片，你对整个系统的反馈来得太晚了。

垂直切片能带来早期反馈（Vertical Slices Give Early Feedback）

解决办法是垂直切片（vertical slices）。agent 从第一个阶段起就横跨所有层级工作。

从一开始，它就在碰数据库、API 和前端。它先搭出一个最小实现，再在此基础上逐步扩展。

展示垂直切片的示意图：从第一个阶段起就贯穿所有层级

这意味着从第一阶段开始，它就能对设计和可行性获得反馈，并看到所有层级是如何集成的。

之后每个阶段都相当轻松，因为它们只是在已被验证集成良好的工作之上继续搭建。

使用「vertical slices」这个说法其实非常管用，因为 agent 对它的含义多少有点概念。垂直切片和曳光弹（tracer bullets）的概念由来已久——可以追溯到《程序员修炼之道》（The Pragmatic Programmer）。

编辑器中打开的 /implement skill 文件

/implement skill（The /implement Skill）

/implement skill 是编排者（orchestrator）。它把大部分工作委托给另外两个 skill。

  • 把工作提交到当前分支

非常简单。真正干活的是 /tdd 和 /code-review。

/tdd skill 文件：展示 TDD 工作流

/tdd skill（The /tdd Skill）

质量就来自 /tdd skill。agent 在反馈最多的时候表现最好，而 TDD 正是制造反馈的绝佳手段。

你先为特性写好单元测试，再去实现它。测试会让 agent 立刻知道实现是否正确。

这个 skill 包含：

  • 什么样的测试是好测试——测试要通过公共接口验证行为，而不是实现细节
  • 关于 mock 与测试的建议
  • 什么是 seam——你进行测试的公共边界
  • 什么样的测试是坏测试——与实现耦合的、同义反复（tautological）的，或是横切出来的
  • 循环的规则——先红后绿、一次只切一片、重构留到审查阶段

只在预先商定的 seam 处测试（Test Only at Pre-Agreed Seams）

**seam（接缝）**是你测试时所依托的公共边界。测试住在 seam 上，绝不针对内部实现。

在写任何测试之前，你要先写下受测的 seam，并与用户确认。没有得到确认的 seam 上，不写任何测试。

这能把测试精力留在关键路径和复杂逻辑上，而不是铺向每一个边界情况。

同义反复的测试（Tautological Tests）

有一个反模式值得点名：同义反复的测试（tautological tests）。这类测试的断言会用与代码相同的方式重新计算期望值。

比如 expect(add(a, b)).toBe(a + b)。这种测试从构造上就注定通过，永远不可能与代码相左。

期望值必须来自独立的事实来源——一个已知正确的字面量、一个算好的例子，或是 spec 本身。

编辑器中打开的 /code-review skill 文件

/code-review skill（The /code-review Skill）

/code-review skill 会对 HEAD 与你指定的固定基点之间的 diff 做一次双轴审查。

它在两个并行 subagent 里跑两场审查：

  • Standards（规范）——代码是否符合这个仓库书面记录的编码规范？
  • Spec（规格）——代码是否忠实实现了来源 issue / PRD / spec？

为什么要两条轴（Why Two Axes）

一次改动完全可能过了一条轴、栽在另一条上：

  • 代码处处符合规范，实现的东西却错了——Standards 过，Spec 挂
  • 代码严格照 issue 的要求做了，却破坏了项目的约定——Spec 过，Standards 挂

分开报告，两条轴就不会互相遮掩。

Standards subagent（The Standards Sub-Agent）

Standards subagent 会拿到：

  • 完整的 diff 命令和 commit 列表
  • 仓库中找到的规范来源文件列表
  • 来自《重构》（Refactoring）的坏味道（smell）基线——Mysterious Name（神秘命名）、Duplicated Code（重复代码）、Feature Envy（依恋情结）、Data Clumps（数据泥团）等

它会报告 diff 违反书面规范的每一处，以及它发现的任何基线坏味道。违反书面规范可能是硬性违规，而基线坏味道永远只是主观判断。

Spec subagent（The Spec Sub-Agent）

Spec subagent 会拿到：

  • diff 命令和 commit 列表
  • spec 的路径或抓取到的内容

它会报告：

  • spec 要求了但缺失或只做了一半的需求
  • diff 中没人要求的行为（scope creep，需求蔓延）
  • 看似实现了、但实现方式可疑的需求

这第二轮检查能极大提升产出的质量。它经常自己动手把真正糟糕的问题修掉。

一手来源与二手来源（Primary and Secondary Sources）

我们可以用之前讲过的 primary source 和 secondary source（一手来源与二手来源）来理解 spec 和代码库。

白板图：Codebase 标注为 Primary Source，Spec 标注为 Secondary Source

spec 本质上是「代码库如何工作」的浓缩版——甚至只是代码库某一部分如何工作的浓缩版。

当然，secondary source 的问题在于它只是一种投影——它是对事物实际运作方式的摘要。

漂移问题（The Drift Problem）

最糟的是，代码库会很快偏离 spec。

换句话说，如果你不持续让 spec 与代码库保持同步，两者就会渐行渐远。

为什么不搞 spec 驱动开发？（Why Not Spec-Driven Development?）

有一种很流行的方法叫 spec 驱动开发（spec-driven development）。其中一种做法是：把这些 spec 存进仓库，让它们取代代码成为事实来源（source of truth）。

然而，正是这种漂移风险让我对这种方法深感恐惧。当你的 agent 探索本地仓库、发现这些讲代码如何工作的陈年旧 spec 时，它很可能去相信那份过时的 spec——secondary source——而不是 primary source。

secondary source 通常更容易探索、更小、更密集。所以一旦它看过这个，就不太可能再去碰那份更冗长、更难探索的 primary source 了。

代码不会说谎（The Code Doesn't Lie）

当然，关键在于：代码库不会就它自己撒谎。看代码库中可执行的部分——函数本身——它们不太可能谎报代码实际在做什么。

前提是你的代码库里没有那些古怪陈旧的部分，比如：

  • 再也没人调用的函数
  • 出于兼容旧有原因而留在系统里的部分
  • 仓库里的一次性原型

归档，而不是删除（Archive, Don't Delete）

说了这么多，结论就是：spec 一旦落进代码，就尽快处理掉。

GitHub issues 列表：已关闭的 issue #4 和它的五张子 ticket，全部标记为已完成

我非常喜欢 issues 这种方式：关掉一个 issue，它就从主视图里挪开，算是被归档了，还带着明确的「已归档」标记。但如果 agent 需要回来看某个东西是怎么实现的、为什么这么实现，spec 还在那里等它翻阅。

为什么 GitHub issues 好用（Why GitHub Issues Work）

不仅如此，团队还能看到它们。如果你的 spec 只是你笔记本上的本地 Markdown，那它只属于你；而躺在 issue tracker 里的 spec 是团队的——可以评审、可以评论，不在决策现场的人也能找到它。

不止如此，把这些 ticket 放在本地环境之外，意味着你切换 worktree、更换笔记本时它们依然安然无恙。状态不会和你本地环境打架。

结论（The Verdict）

所以我想传达的就是这句话：把你的 spec 归档。

你的 spec 本来就是定义一段工作的临时产物，而不是「代码如何工作」的事实来源。

随堂测 · Quiz

spec 下最后一张 ticket 已合并，工作已经上线。你该怎么处置这份 spec？

  • 在 issue tracker 里关闭它，让它归档但仍可查找
  • 把它提交进仓库，当作解释代码如何工作的文档
  • 直接删掉，让任何过时内容都无从再被读到
  • 保持打开状态，代码每次变动都跟着更新它

答案与解析

关闭的 issue 会移出主视图，但仍留在那里，供 agent 或队友随时回看。把 spec 提交进仓库，恰恰会让 agent 去相信一份日渐老化的摘要而不是代码。删掉它则白白扔掉了本可免费获得的历史记录。而手动保持同步，正是你原本想避开的维护负担。

代码已经向前走了，仓库里还躺着一份旧 spec，为什么危险？

  • 它是 secondary source，agent 会宁可信它也不信代码本身
  • 它很冗长，读它会烧掉 window 的大块容量
  • 它与 ticket 冲突，agent 无法调和这种冲突
  • 它只存在于你的笔记本上，团队里没人能读到

答案与解析

spec 是代码库的一种投影，而且比代码更小、更密集，所以 agent 发现它就会停在原地，再也不去读那份不会对自己撒谎的 primary source。体积不是危险所在——spec 才是紧凑的那个。到那时 ticket 早已不在。而「私人可见」只是支持 issue tracker 的理由，并不是漂移伤人的原因。

# Rerouting：当目的地改变时（Rerouting: When The Destination Changes）

想象这样一个场景：你有一份 spec，并为它拆好了一些 ticket。走到一半——也许你正在逐个审查交上来的 ticket——突然意识到：糟糕，这个路子整个就是错的。

当两个 ticket 交上来、我们意识到必须改方向时，该怎么办？

Ticket 是一次性的（Tickets Are Disposable）

这里你需要意识到的一点是：ticket 是一次性的。

如果我们意识到这批 ticket 不对——也许前两个已经实现了，但后两个还没实现——那就直接把还没实现的那些 ticket 删掉就好。

白板，上面写着「Tickets - Disposable」和「Spec - Editable」的标签

然后我们回到 spec——而 spec 是可以编辑的。

所以我们可以就当前所处的位置来一次 grilling session。两个 ticket 做出来我们都不满意，那就需要回到 spec 去修改它。

Spec 就是目的地（The Spec Is The Destination）

换句话说，spec 就是目的地，而我们正在改变目的地。

我会做的是：回到 spec，再开一次 grilling session，等我对 spec 的修改满意之后，就重新生成一批 ticket。

这批新 ticket 可能会让工作范围略有变化，所以最后我们要做的事情也许会多上一点点。但这意味着，我们已经找到了从当前位置通往新目的地的路线。

白板，六个 ticket 方块，下方的 spec 长条向外延伸

整体流程（The Flow）

整个流程长这样：

1. 「哦不，这得改」

意识到你想改变目的地。事情没有按你期望的样子发展。

2. 关掉 ticket

删除所有尚未实现的 ticket。但 spec 要留着，因为你要修改的正是 spec。

3. 修改 spec

用 /grill-me 来调整 spec，说清楚你想改什么。最好在一个新的 session 里进行。

4. 重新生成 ticket

等你对 spec 满意了，就基于当前所在的位置重新生成 ticket。用 /to-tickets 来重新生成新 ticket。

所以你大概率不用扔掉已完成的工作——除非它真的真的太糟。然后你就从那个节点继续实现。

5. 继续实现

用 /implement 来实现新的 ticket。

如果你需要在流程中途改方向，这就是一份简洁好用的小抄。

为什么要两份文档？（Why Two Documents?）

我想为这个话题加一小节视频，因为总有人问我这个问题，而它其实是个相当简单的过程。

这也正是我们采用两份文档设计的原因：让 spec 充当目的地，而 ticket 完全是一次性的。

如果它们都挤在同一份文档里，事情就会变得有点混乱。

随堂测 · Quiz

两个 ticket 交上来，你审查成果时发现整个路子都错了。第一步做什么？

  • 删掉尚未实现的 ticket，保留 spec
  • 回滚已经完成的两个 ticket，spec 从零重写
  • 废弃现有 spec，在保留 ticket 的旁边另写一份新 spec
  • 先做完剩下的 ticket，再在 review 里修正方向

答案与解析

ticket 是一次性的，spec 是可编辑的，所以该扔的是 ticket。已经实现的工作通常保留，而不是回滚。在旧 ticket 旁边另写新 spec，会让那些 ticket 依然指着你刚刚放弃的目的地。而明知道是错的还硬做完，只会给你攒下更多要撤销的代码。

为什么目的地和路线图要放在两份独立文档里，而不是一份？

  • 这样目的地可以编辑，而路线图可以整个扔掉
  • 这样两份文档都不会大到塞不进一个 context window
  • 这样一份文档归你所有，另一份完全归 agent 所有
  • 这样在任何计划写出来之前，就能先审查目的地

答案与解析

两份文档的生命周期不同，混在一份里，想扔掉其中一半时就会很混乱。长度并不是拆分的理由。两份文档也不专属于你们中的任何一方——spec 是你和 agent 一起 grill 出来的，ticket 也是 agent 从它生成的。而单独一份文档照样可以分阶段审查。

# /goal 命令（The Goal Command）

大家经常问我的一个问题就是：为什么我们不用 /goal 来实现 spec？

/goal 的思路（The /goal Theory）

思路是这样的：先创建一份 spec，然后用 /goal——这是许多 harness 都有的功能，让 agent 在单个 context window 里追逐一个目标，直到完成为止。

这个目标就是目的地，而且是一份被写得非常非常明确的目的地，看起来简直是 /goal 的完美用例。

示意图：上方是 spec 的定义，下方是 /goal 的定义

问题所在：dumb zone（The Problem: The Dumb Zone）

然而，我见过的所有 /goal 实现，都没有真正利用 smart zone。全部工作都在单个 context window 里完成，靠 auto-compaction（自动压缩）来撑着。

于是你最后得到的就是：开头一小段 smart zone，然后是一大片 dumb zone。

每次我尝试这条路，看到的都是同一副景象。所以我依然认为 Spec-and-Tickets 的方案好过 Spec-and-/goal。

保留余地：如果 auto-compaction 变好了（The Caveat: If Auto-Compaction Improves）

不过，如果 auto-compaction 有朝一日好到 dumb zone 不再是问题，那我会认为这是一个非常棒的设置。

你依然要做所有围绕 spec 的思考。只不过，你如今把它交出去的那个东西，负责：

  • 它自己的 context 管理
  • 它自己的 ticket 管理
  • 理解所有需要完成的任务

而且最后你仍然可以做一次大 code review，检查成果是否符合 spec。

我目前的建议：用 ticket（My Current Recommendation: Use Tickets）

但就目前而言，我的建议依然是改用 ticket。

示意图：四个等宽矩形，每个都标着绿色的「Smart」，下方的时间条更短

为什么 ticket 能给你更多控制（Why Tickets Give You More Control）

Ticket 能给你的控制力多得多。而且我认为它们通常更省钱，因为你大部分工作都发生在许多个 smart zone 里。

从 spec 生成 ticket 往往是一件非常非常快的事，通常只要花我几分钟。

在我的一些工作流里——课程里没有细讲的那些——我甚至在 AFK 状态下生成 ticket，连审查都省了。

对比：Spec-and-Tickets vs Spec-and-/goal（Comparison: Spec-and-Tickets vs Spec-and-/goal）

方案 上下文管理 成本 区域质量
Spec-and-Tickets 多个 smart zone 通常更便宜 大部分时候很聪明
Spec-and-/goal 单个 context window 可能更贵 smart zone 很小，dumb zone 很大

我觉得，眼下这套做法比直接用 /goal 稳得多。

你的体验可能不同（Your Experience May Vary）

当然，如果你得到了和我不同的结果，如果你比我相信你的 auto-compaction，我很乐意知道——而且如果它真能跑通，/goal 绝对是个好点子。

干得漂亮，我们下节课见。

随堂测 · Quiz

你的 harness 提供了一条命令，能在单个 context window 里追逐一个目标直到完成。你手上也有一份写得非常明确的 spec。为什么还要把它拆成 ticket？

  • 单个 window 只给你一小段 smart zone，剩下的一大片都是 dumb zone
  • spec 太模糊，当不了 agent 追逐的目标
  • 最后你根本没有机会对照 spec 审查成果
  • 从 spec 生成 ticket 太慢，goal 正好跳过这一步

答案与解析

单个 window 依赖的是 auto-compaction，于是整个过程开头聪明、余生愚蠢；而 ticket 让你待在好几个 smart zone 里，往往还更便宜。spec 恰恰是一份写得非常明确的目的地，这正是 goal 这个点子起初显得诱人的原因。最后你依然可以做一次大 review，检查成果是否符合 spec。而把 spec 变成 ticket，通常也就花几分钟。

在「单个 window 里追逐一个目标」成为好方案之前，什么必须先进步？

  • auto-compaction，要好到 dumb zone 不再是个问题
  • context window，要大到能一次装下整个项目的工作
  • token 价格，要低到让一次超长运行成为便宜的选择
  • code review，要能在与实现相同的 window 里运行

答案与解析

拦路的是 dumb zone，而被指望管住它的正是 auto-compaction。更大的 window 帮不上忙，因为问题出在 window 后半段的质量，而不是空间不够用。价格只是症状，不是病根。而 review 本来就可以在事后用一次大检查完成，运转良好。

# 落实你的 coding standards（Enforcing Your Coding Standards）

Commit Map（提交对照）

add-coding-standards 本课起点：仓库里加入了一份只有一行的 CODING_STANDARDS.md

/implement skill 里有这么一行，很容易一眼扫过：

Once done, use /code-review to review the work.

值得在这里停下来。code review 正是你把自己的 coding standards 强加给 agent 的地方。

/implement skill 中展示 code review 那一行的地方

三层检查（Three Levels Of Checks）

在代码交付之前，你真正想让它跑上三层检查。

层级 能抓住什么 代价是什么
automated checks（自动化检查） 机械性错误 零
automated review（自动化审查） 「判断型」的问题 token
human review（人工审查） 其余的一切 你的注意力

自动化检查（Automated Checks）

Automated checks 指的就是 linting、typecheck 和单元测试。它们重要，是因为它们是确定性的：agent 跑一遍，得到的永远是同样的通过或失败。

运行它们也不花 token，几乎是免费的。要是所有事都能靠 automated checks 解决，那我们就活在梦里了。

但 automated check 抓不住所有 bug。测试套件只能证明你断言过的那些性质。所以你还需要在上面再叠一层审查系统。

人工审查（Human Review）

在 AI 出现之前，这层审查系统就是人。有人会看着 pull request 说：这看起来不对。这个测试做的根本不是我们以为的事。你考虑过这种做法吗？

换句话说，人在提供定性反馈。说的是：这个我不太确定。

而 human review 从来都是开发里最没人喜欢的环节。你手头总攒着一摞等着你去 review 的 pull request，非常痛苦。

堆成一摞、等着被 review 的 pull request

自动化审查（Automated Review）

现在 agent 能帮上忙了。Automated review 就是让 agent 来审查你的工作，自己给出那些定性反馈。

关键在于，它并不取代 human review，而是让 human review 变轻松——因为 agent 已经把 diff 通读了一遍，做完了首轮筛查。有 automated review，能抓到的问题比你赤手空拳时更多。对大多数类型的工作，你依然需要一个人在最上面做 sanity check。

code review skill 做的正是这件事。你在一个 context window 里实现，再在一个全新的 window 里审查。

两条审查轴线（The Two Axes）

这次审查沿着两条轴线展开。Spec 轴问的是：代码是否忠实地实现了当初要求的东西：

- **Spec** — does the code faithfully implement the originating issue / PRD / spec?

另一条轴是 standards。coding standards（编码规范）很重要，因为你不想让 agent 把同一个错误一次又一次地重犯。这些「掌舵指令」总得有个安身之处。

把它们塞进 CLAUDE.md 很难受，而且有实实在在的坏处。不过 code review 是个有趣的特例，因为这个 skill 允许你定制。你可以创建自己的 CODING_STANDARDS.md 文件。

CODING_STANDARDS.md

这个文件就静静躺在那里，记录着这个仓库的 coding standards。当你发现 agent 干了什么怪事，就把它写进 standards 文件，下一次 review 就会把它抓住。

一份全新的文件可以只有一行：

Don't do stupid stuff.

skill 会在它的第三步找到这个文件——那一步是在弄清楚这个仓库在哪里写了「代码该怎么写」：

Anything in the repo that documents how code should be written, such as `CODING_STANDARDS.md` or `CONTRIBUTING.md`.

这一步，正是你要写进去的那道接缝。

为什么 standards 应该放在 review 里（Why Standards Belong In Review）

这样做之所以合理，是因为 code review 受到的约束远比实现少。

实现一个东西时，你得探索它在代码库里的落点，写完所有文件，再调试确认它真的能跑。三重负担，全压在同一个 context window 上。

code review 一样都不沾。你不需要探索，因为探索已经完成，正确的文件直接递到你手上。你不需要做多少改动，因为你要做的只是阅读现成的东西。你也不必背负「验证一切能跑」的责任，因为测试早已写好、跑过。

/implement code review
探索代码库 要 不用
编写文件 要 不用
调试与测试 要 不用

所以，把 coding standards 装进 code review，远比逼着实现者一次写对要合理得多。审查用的 agent 在 context window 里有充裕得多的空间，身上的要求也少得多。

实现者与 code review agent 所背负任务的对比

真实的 standards 文件长什么样（What A Real Standards File Looks Like）

一份成熟的 standards 文件是松散的，这完全没问题。里面每一行的来历都一样：你发现 agent 干了件蠢事，然后把它记了下来。

课程视频管理器仓库里真实的 CODING_STANDARDS.md 文件

Context menu items should always include a leading icon (from `lucide-react`), matching the style of the surrounding items. When adding a new menu item, pick an icon that conveys the action.

这条规则的存在，是因为不知为何，agent 就是不肯加图标。

All files in `./app/routes` will be exposed publicly as routes. Do not include test files or utility files there.

你当然可以把这样一个文件拆开，把其中一部分放到 context pointer（上下文指针）后面。如果某条规则只对前端工作有意义，那它就该待在前端那里。但由于 standards 文件只在 code review 时才被加载，它的体量远不像常驻的掌舵文件那么要紧。长得相当大也无所谓。

白送的基线（The Baseline You Get For Free）

哪怕完全没有 standards 文件，Standards 轴线也自带一组 code smell（代码坏味道），取自 Martin Fowler 的 Refactoring 一书：

skill 中列出的 Martin Fowler《Refactoring》一书中的 code smell

- **Feature Envy** — a method that reaches into another object's data more than its own. → move the method onto the data it envies.

Shotgun Surgery、Divergent Change、Mysterious Name。这些都是经典的编程术语，agent 本来就了如指掌。所以哪怕你什么都没写下来，review 也常常能有所发现。

你自己的文件叠在这条基线之上，并覆盖它。如果你的仓库认可了基线本会标记的某种做法，那条标记就会消失。

别冲 agent 发火（Don't Shout At The Agent）

有一个值得养成的习惯。下次你完成一次实现、发现不喜欢的地方时，别冲 agent 发火。

把它写进 CODING_STANDARDS.md，让审查者去抓住它。

干得漂亮，我们下节课见。

随堂测 · Quiz

你反复发现 agent 写的代码违反了仓库的某条约定。这条规则该写在哪里？

  • 写进 CODING_STANDARDS.md，让 review 抓住它
  • 写进 CLAUDE.md，让实现者每次都读到
  • 写进提示词，每项工作都重申一遍
  • 哪儿也不写，反正 linter 会抓住它

答案与解析

实现本身已经把三重负担压在一个 context window 上：探索、写代码、调试。review 一样都不沾，所以才有空间装下你的 standards。写进 CLAUDE.md，不管规则适不适用，每个 window 都要为它买单；写进每次任务的提示词，就成了需要你自己记住的规则；而 linter 能强制执行的约定，本来就不用写下来。

automated check 和 automated review 的区别是什么？

  • check 是确定性的、免费的；review 是定性的、要花 token
  • check 跑得更快，但两者抓住的是同一类问题
  • check 在提交前运行；review 在提交后运行
  • check 由工具运行；review 只能由人来运行

答案与解析

linting、typecheck 和测试每次运行都给出同样的通过或失败，而且分文不花——这恰恰说明它们给不了判断力。review 是判断这一层，用 token 付费。两者可以在同一阶段运行，review 既可以由 agent 跑，也可以由人来跑。

你在一个没有 CODING_STANDARDS.md 的仓库里运行 code review skill。Standards 这条轴线靠什么工作？

  • 一套内置的 code smell，取自《Refactoring》
  • 什么都靠不上，Standards 轴线报不出任何发现
  • 当时 CLAUDE.md 里碰巧有什么就用什么
  • 先通读整个代码库推断出的约定

答案与解析

Feature Envy、Shotgun Surgery、Divergent Change 等等是随 skill 自带的，所以哪怕仓库什么都没写下来，也能得到一次 review。你自己的文件是叠加在这条基线之上、覆盖它，而不是取代它。

# 向 Matt 提问（Ask Matt）

Commit Map（提交对照）

学完这门课程时，你手里多半还攒着问题。这很正常。问题在于，从「有了疑问」到「得到解答」之间的空档，你该怎么办。

你随时可以在 Discord 上问我。我很乐意回答，社区的其他人也是。但在等回复的间隙，有一样东西你可以试试。

有一个工具，能让你在我本人不在场的情况下征求我的建议。

重置到引入 skill 的课程节点（Reset To The Skill）

打开终端，重置到加入这个 skill 的那节课。

npm run reset add-ask-matt-skill

这个 commit 会把一个 /ask-matt skill 放进仓库。把当前分支重置到它上面，打开你的 agent，就可以向 Matt 提问了。

问它一个真问题（Ask It A Real Question）

这个 skill 吃的是情境，不是关键词。下面是我抛给它的那个问题。

/ask-matt What's the best flow for fixing a bug once I've finished doing an implementation on a spec and all the tickets are closed?

这是一个真实会遇到的处境。spec 已经建好，每个 ticket 都已关闭，然后发现有东西坏了。眼下没有哪条命令是显而易见该敲的，因为你一直在走的那条流程已经到头了。

它的回答（What It Answered）

router（路由）的开场白是这样的。

**Short answer: `/clear`, then `/diagnosing-bugs`.**

两步棋。先清空 context，因为 spec 这条线已经用尽，而 bug 是一个新的起点，不是这次构建的延续。然后伸手去拿处理 bug 的那个 skill。

它给的不止这句标题。它说，先检查你能否用一条命令让 bug 变红（复现出失败）：如果能，而且原因一目了然，那就写下失败的测试然后修掉它。如果不能，那才是诊断 skill 上场的时刻。它还点名了两件不要做的事。不要去 triage 这个 bug，因为 triage 只用于那些不是你亲手制造出来的 issue。也不要重开已关闭的 spec，因为一份被证明是错的 spec 是一个新想法，不是打补丁。

它知道课程没讲的 skill（It Knows Skills The Course Does Not Cover）

它推荐的那个 skill，我们在课程里没遇到过。但它确实存在于我真实的 skillset（技能集）中。

这正是关键。这门课程覆盖了主流程和相当多非常重要的 skill，但没有覆盖 skillset 里的一切。还有东西要学，而 /ask-matt 就是你学习它们的方式。它列在 Getting Started（入门）之下，是快速熟悉其余 skill 的好办法。

所谓 flow，是贯穿各个 skill 的一条路径，不是单个 skill。大多数工作都沿着一条主 flow 前行，有几条「匝道」汇入其中，其余的则各自独立，或是垫在底下的一层「词汇表」。当你说出自己的处境时，router 会把你放上某条 flow 的正确一步——这个答案往往和「名字与你用词匹配的那个 skill」并不相同。

阶段边界清单（The Phase Boundary Checklist）

skill 本身内藏一个特别有用的东西：阶段边界清单（phase boundary checklist）。

一个 phase（阶段）就是 session 里的一块工作：grilling、实现、QA。边界则是两块之间的缝隙，而你要在哪里决定 context window 的去留。这个决定是真的难做：你有五个选项，却没有显而易见的挑选办法。

选项 作用
Continue 留在当前 session，完全不切换 context。
Clear 清空 context window，从零开始。
Handoff 写一份便于携带的 markdown 文件，用它随处播种一个新 session。
Subagent 把任务送进它自己的 context window，干完只带回一份报告。
Compact 压缩当前 context，用摘要播种一个新 session。

所以当你拿不准该 continue、clear、hand off、丢给 subagent 还是 compact 时，这个 skill 能带你走一遍。它从上到下过一遍这些选项，第一个「是」胜出——这就把一种模糊的感觉变成了一组有序的问题。

对它的回答打个问号（Take Its Answers With A Pinch Of Salt）

回头看看它给我的那个答案。它说要去 clear。要我说，那里最好的选择恐怕是 compact，因为实现阶段的一些 context 值得带进捉虫之旅。而且说实话，你也许根本用不上 /diagnosing-bugs skill——那个 skill 只为非常非常刁钻的 bug 而设。如果是个简单 bug，你自己可能就能搞定。

所以，把它当成任何一个 agent 来对待。它是 router，不是神谕。它是你围绕 skill 提问、弄清下一步可能想用什么的好办法，但对它给出的东西，你依然要过一遍自己的判断。

如果你发现它给出了什么奇怪的答案，就去 skills 仓库本身提个 issue。router 就是这么变好的。

大家发现，在啃 skill 的过程中，把它当作第一站去弄懂那些还不太明白的东西，非常有用。

随堂测 · Quiz

/ask-matt 这个 skill 还给你的是什么？

  • 一条建议：接下来该走哪条 flow、用哪个 skill
  • 把你描述的改动直接实现好的成品
  • 根据你描述的情境写好的一份 spec
  • 仓库里安装的每一个 skill 的清单

它是一个 router。你说出自己身处的情境，它就说出与之匹配的 flow，以及下一步该敲什么。它不会替你把改动做出来，不会写 spec，也不是一份目录清单。另外三个是别的 skill 的活儿。

  • 行动之前，先拿它和你自己对局势的判断掂量掂量
  • 原样执行这两条命令，毕竟 skill 掌握着完整的地图
  • 无视它，因为 router 又看不见你的代码库
  • 反复问它，直到两次运行给出同一个答案
