前置要求（Prerequisites）

这门课的前置要求其实就两条：

  • 你能读懂代码吗？能就好。
  • 你会用终端吗？

会读代码能让你更轻松地在代码库中穿梭，弄清楚到底发生了什么。你甚至不一定需要会写代码。

安装 Node（Installing Node）

这个项目用 Node.js 在你的电脑上运行 JavaScript。检查你是否已安装：

node --version

当前安装的版本是 22.21.1。你应该选 LTS（Long-Term Support，长期支持）版本，它最稳定。这些版本标签的含义如下：

标签 含义
LTS 长期支持——最稳定，推荐
Current 最新、最花哨的版本
EOL 已到生命周期终点——不再受支持

你可以从 Node.js 下载页安装 Node.js，目标是 22 或 24 版本。如果装完后终端里找不到 node，把终端关掉重开，刷新 PATH：

node --version

Node 自带 npm（Node Package Manager）。也检查一下它是否可用：

npm --version

设置数据库（Setting Up the Database）

这个应用把数据存在一个本地文件里。新克隆的仓库不包含它，所以需要两条命令来构建它。

首先，运行以下命令创建数据库：

这会在项目根目录创建一个本地 data.db 文件。然后，用种子数据填充它：

npm run db:seed

这些脚本和其他脚本一起定义在 package.json 里：

{

"db:migrate": "...",
"db:seed": "...",
"dev": "..."

如何运行练习（How To Run the Exercises）

Commit 地图

main 本课起点：课程仓库，与你刚克隆下来时完全一致

这门课的教学方式是给你布置练习去完成——规划这个功能、加上这个改动、修掉这个 bug。所有代码课程都有一个共同的难题：进度漂移。你做了一个视频里没做的改动，三节课之后，你的代码库就和屏幕上的不是同一个了。

为了解决这个问题，项目里内置了三个 CLI 工具，让你可以按需跳到任意练习的起始状态。

重置到练习检查点（Reset to an Exercise Checkpoint）

  • 运行 npm run reset 查看完整的课程检查点列表
npm run reset

这会打开一个交互式选择器，按顺序列出课程中的每个检查点。你可以输入文字搜索——比如输入 try the cli 就能筛到 try-the-cli。

npm run reset 的交互式选择器，显示课程检查点列表

  • 选中一个检查点，然后选择 Reset current branch

工具会把你的分支回退到那个确切的 commit。你会看到类似这样的输出：

Resetting to try-the-cli...
✓ Reset to try-the-cli

你也可以直接传入检查点名，跳过选择器：

⚠️ reset 是破坏性操作。 它会回退整个工作分支——不只是练习涉及的那几个文件。未提交的工作会全部丢失。在 reset 之前，先把想保留的东西 commit 或 stash 起来。

用 cherry-pick 保留你自己的工作（Keep Your Own Work With Cherry-Pick）

  • 在 package.json 里加一个脚本用来试验，比如：
"foobar": "echo 'foobar'"
  • 通过 VS Code 的源代码管理面板（Ctrl+Shift+G）或终端提交这个改动
  • 运行 npm run cherry-pick 而不是 reset
npm run cherry-pick

它显示的是同一个选择器，但不会回退你的分支，而是把检查点的 commit 应用到你现有工作的上面。你的 commit 会原封不动地留在下面。

✓ Successfully cherry-picked lesson try-the-cli

数据库 Migrations（Database Migrations）

Commit 地图

try-the-cli 本课起点：已应用 CLI 检查的仓库，尚未做任何 schema 改动

make-a-schema-change 跟练检查点：schema.ts 中新增 notes 列，外加对应的 migration

之所以有这一节，是因为很多上过这门课的同学都在这一点上栽过跟头。如果你已经熟悉数据库是什么、数据库与源代码的区别，可以跳过本节；但这些信息相当关键，值得深入讲一遍。

两个单元（The Two Units）

单元 它是什么 示例
源代码（Source code） 你编辑的、用来改变应用行为的文件 app/db/schema.ts、app/components/dev-ui.tsx
数据库（Database） 独立存放实际数据的地方 data.db（磁盘上的一个文件）

这个项目用的是 SQLite，所谓数据库其实就是磁盘上一个叫 data.db 的文件。而源代码，比如 app/components/course-image.tsx 和 app/components/dev-ui.tsx，是可读的文本，你可以修改它们来改变应用的行为。

文件树显示 data.db 位于仓库根目录，与源代码文件夹并列

如果打开 app/db/schema.ts 看一眼，你会发现源代码实际上定义了数据库的形状——声明了表和它们的列。

数据库 Migrations 是如何工作的（How Database Migrations Work）

示意图：source code 与 database 之间的方向性关系，migrations 是中间那一步

关键洞察： 源代码定义了数据库应该长什么样，但在数据库跟上之前，你需要手动做点什么。

这一步就是 database migration：手动更新数据库，让它与 schema 声明的样子保持一致。

之所以要手动做，是因为传统上数据库里存着相当重要的信息：你的全部用户数据，神圣不可侵犯的东西。在真实应用中，你需要手动做 migration 来让两者同步。

这意味着你的源代码和数据库必须一起管理版本：

  • 如果源代码变了，但数据库没有跟着 migrate，你很可能会收到报错。
  • 在这个项目里，app/db/schema.ts 是源代码，data.db 是数据库的实时状态。
  • 要做 migration，运行：
npm run db:migrate

动手 Migration 实操（Hands-On Migration Walkthrough）

要看实际效果，打开 app/db/schema.ts，在一个新终端里运行 npm run reset。选择 make-a-schema-change 这节课的 commit（选择器里显示为 "Make a Schema Change"），重置当前分支。

这个改动非常细微：它在 schema.ts 的 courses 表里加了一个 notes 列。

description: text("description").notNull(),
+ notes: text("notes"),
salesCopy: text("sales_copy"),

它还在 drizzle/ 文件夹里生成了一个新 migration 文件 0003_lean_hex.sql：

ALTER TABLE `courses` ADD `notes` text;

drizzle/ 文件夹中的四个 migration SQL 文件

drizzle/ 文件夹基本上就是所有已应用数据库 migrations 的历史。从新到旧依次是：

  • 0003_lean_hex.sql——给 courses 加 notes 列 （刚加的）
  • 0002_lying_shriek.sql——添加优惠券
  • 0001_cynical_sunspot.sql——给 lessons 加 github_repo_url
  • 0000_dizzy_fenris.sql——初始 migration

这些文件将由 agent 负责管理，并随着应用发展不断增多。你不必太直接操心它们。

排查 Schema 不匹配错误（Debugging the Schema Mismatch Error）

就算只是这么一点小改动，如果不 migrate 就运行开发服务器，也足以把事情搞坏。

打开 http://localhost:5175，进入某个具体课程。首页看起来正常，但课程详情页报错了。

浏览器中报错的课程详情页

看终端，有一个 SqliteError：

no such column: notes

它来自 getCourseBySlug 函数。schema 文件已经改了，但 data.db 还没有更新到与之匹配。

在重置源代码状态时，你会经常遇到这种情况。npm run reset 只动源代码，它不会替你运行 db:migrate。

解决办法是另开一个终端，运行：

npm run db:migrate

运行 npm run db:migrate 的终端

跑完之后刷新页面，一切正常。data.db 和 schema 现在同步了。

搞坏并重置你的数据库（Breaking and Resetting Your Database）

还有一点值得说明：你随时可以把数据库搞坏，完全没关系。这不是生产数据。

你在前面的设置环节运行过一个 seed 脚本来给数据库灌数据。它做的事情是：

  1. 删掉所有表
  2. 重建它们
  3. 灌入一堆虚拟数据

虚拟数据里包括管理员 Alex Rivera，以及讲师 Sarah Chen 和 Marcus Johnson 等用户。

如果你在测试某些场景、需要特定的种子数据，agent 可能会想更新这个脚本。

要记住的流程（The Flow to Remember）

当 agent 修改了 schema.ts，你要么让 agent 自己去 migrate，要么手动 migrate。运行 npm run reset 之后尤其如此，因为 schema 很可能与数据库失去了同步。

三个关键脚本的速查表：

命令 作用
npm run db:generate 根据改动后的 schema.ts 向 drizzle/ 写入新的 migration 文件
npm run db:migrate 把待执行的 migration 文件应用到 data.db
npm run db:seed 清空数据库并重新灌入虚拟数据

任何涉及 schema.ts 的 npm run reset 之后，一定要运行 npm run db:migrate。

重置为干净状态（Resetting to a Clean Slate）

上这门课的大多数人，都已经折腾过某种 agentic 配置。

你可能试过：

  • 一些 MCP server
  • 调来调去的设置
  • 装了一大堆 skills
  • 插件

这些多半意味着你把环境配置过度了。大多数人来上这门课时，配置都已经堆得太多。

删掉它（或者先备份）（Delete It (Or Back It Up)）

这里的建议很可能是全部删掉。其中很多东西你根本用不上。从小巧的起点开始工作是最好的。

但如果你很珍惜这些配置、想留着它们，那一定要先备份。

让你的 agent 来做（Let Your Agent Do It）

推荐的做法是让你的 agent 来干这件事。你的 agent 应当是它自己配置方面的专家。

用下面的 prompt，复制粘贴给你的 agent，让它把一切恢复到一张白纸的状态，同时备份好所有东西。

You are the expert on your own configuration. Reset me to a clean slate (the config a fresh install would have) with everything I have now preserved so you can restore it on request later.

**1. Inventory.** Consult your own documentation for where your configuration lives, then find every piece of it that applies to me, both global (user-level) and local (this project). Cover settings files, instruction/memory files, MCP servers, skills, plugins/extensions, subagents, custom commands, hooks, and output styles. Report every path you find with a one-line description of what it does. Done when every location named in your docs has been checked and reported, including the ones that turned out to be empty.

**2. Back it up.** Create `~/agent-config-backup-<today's date>/` and MOVE each item there, mirroring its original path inside the backup so the layout is self-describing. The backup is the only surviving copy, so verify each move landed before continuing.

**3. Write the restore instructions.** Add `RESTORE.md` at the root of the backup listing every backed-up item, its original absolute path, and the exact commands to put it all back. Written well enough that a future agent with no memory of this conversation can restore everything from that file alone.

**4. Verify.** Re-run the inventory from step 1. Report what remains and confirm each remaining item is a genuine default rather than something I configured.

Keep me signed in - leave auth, credential, and session files exactly where they are. Keep this project's source code untouched; only configuration moves.

Finish with a table of what was moved and the one-line command I can give you later to restore it.

这样你之后就可以提醒它从这份备份里恢复。这应该相当简单，因为这些配置大多基于文件——它会把所有东西存到一个单独的目录里，随时可以按需恢复原状。

运行时会发生什么（What Happens When You Run It）

Claude Code 终端运行重置 prompt

在 Claude Code 里，它会先查阅自己的文档，弄清配置都存在哪里，然后把所有东西盘点一遍。

备份完成后，你的 agent 会给你一句简短的 prompt，之后可以用它恢复一切。大概像这样：

安装 Request Logger（Installing The Request Logger）

agent 常常让人觉得像个黑盒。你输入一条消息，harness 向 model provider 发出一个请求，而你永远看不到里面装了什么——看不到 system prompt，看不到 tool 定义，什么都看不到。

课程仓库自带一个 request logger 来解决这个问题。它是一个小型代理，架在你的 agent 和 model provider 之间，把一切原样透传，并把每个请求的可读副本写到磁盘上。

完成步骤（Steps To Complete）

启动 Request Logger（Start The Request Logger）

  • 在终端里，从仓库根目录启动 request logger：
npm run request-logger

第一次运行时，它会问你用的是哪个编码 agent。如果你的 agent 能用不止一个 model provider，它还会问是哪一个。然后它会问要不要记住你的答案，这样只需问一次。

随后它会启动一个监听 localhost:8787 的本地 web server，并打印出针对你所选 agent 的精确启动命令。

终端显示 request logger 正在监听 localhost:8787

  • 在第二个终端里，复制粘贴 request logger 打印出来的命令并运行

这条命令会启动你的 agent 并让它指向 logger。不要自己手写。logger 会为你的 agent 生成这条命令，打印出来的就是正确的。有些 agent 还需要一个小配置文件，logger 也会把它打印出来。

这条命令会在启动时设置好一切，所以你的 agent 必须带着它启动。

  • 给 agent 发一条短消息，确认它像平常一样响应

代理会把一切原样透传。你的 agent 用起来应该毫无区别。

request logger 运行期间 agent 正常响应

浏览日志文件（Explore The Log Files）

  • 打开 request-logger/logs/ 文件夹

发送一条消息后，你会看到带时间戳的文件出现。每个时间戳都是 UTC 时间。

request-logger/logs 文件夹中的带时间戳日志文件

  • 打开最新的 .md 文件——这是可读渲染版，从这里看起

每个请求对应的三种文件类型：

文件 内容
.md 可读渲染版——从这里看起
.request.txt 逐字节的请求体原文
.response.txt 原始响应流
  • 注意，你发的每条消息可能对应不止一条日志记录

Claude Code 会在启动时发一个配额探测——一个刻意为之的单 token 请求，用来检查订阅额度余量。这个探测会作为一条独立的日志记录落地（通常是一个 429 错误），与真正的 turn 分开。所以一条消息出现两条记录是正常现象，不是重试。

浏览可读渲染版（Navigate The Readable Render）

  • 熟悉一下 .md 文件的 XML 标签结构

这个文件用 XML 标签而不是 Markdown 标题来划分区块，因为捕获的内容本身就满是 Markdown 标题。各区块如下：

<meta> - timestamp, model, endpoint, status
<headers> - request headers (authorization is redacted)
<request>
<params> - max_tokens, stream, thinking settings
</params>
<system-prompt>
</system-prompt>
<tools>
</tools>
<messages>
</messages>
</request>
<response> - stop reason and token usage
</response>
  • 滚动浏览 <tools> 区块，注意它相对于文件其余部分有多大

工具 schema 是 JSON，占了文件的大头。对于一个像 Hello! 这样只有一个词的 prompt，光这一块就可能超过 1,000 行，而整份文件大约 1,300 行。

打开的可读 .md 日志文件，显示庞大的 tools 区块

  • 找到 <system-prompt> 区块，读一读里面的内容

这是你的 agent 在你还没输入任何内容之前就附加到每个请求开头的一份常设简报，内容包括你的工作目录、平台以及 session 使用指引之类。

  • 找到 <messages> 区块，在里面定位你真正的消息

你还会看到在你的消息之前注入了一个 system-reminder turn，带着当前日期之类的 context。它是一条消息，不属于 system prompt 的一部分——只有靠 logger 你才能看到它。

  • 查看 <response> 区块里的 token 用量数字

哪怕只是一句 Hello!，也可能导致数以万计的 cache token 被读取。完整的 system prompt 和 tool 定义每一轮都会发送。

现在你可以把 request logger 关掉了。课程后面再需要它的时候，我会特别提醒。
