steering map：转向地图（The Steering Map）

每次开启一个全新的 session，agent 醒来时对你的工作方式一无所知。这不是 bug——这正是 stateless（无状态） 的含义。model 不会把任何东西从一个 session 带进下一个 session，所以你的约定、你的边界情况、你想在项目里固化的那些模式，在你清空 context 的那一刻就统统消失了。

steering（转向） 要回答的问题是：如何跨越不同的 session 去引导 agent 的行为。哪些指令应该每次都送达 agent？又该如何送达，才不必每次继续干活时都重新复述一遍？

那么，这些 steering 指令应该住在哪里？ 这就是本节要回答的问题。

理解 context load（Understanding Context Load）

在回答之前，我们得先解决一个概念——本节余下的内容全都建立在它之上。

任何你预先加载给 agent 的东西，你都要在每一次 model provider request（模型供应商请求）上为它买单。

一个 session 可以包含多个 turn（轮次），每个 turn 又包含许多 model provider request——你发出一个请求，收到一个响应。单个 turn 可以持续 15 分钟，包含数百个 model provider request。一个 session 里可以有非常非常多的 turn。

示意图：一个包含三个 turn 的 session，每个 turn 中有多个 model provider request，以浅蓝色圆点表示

每个 model provider request 都会把全部历史连同所有新增内容一起带上。你在 context window 靠前位置添加的任何一条小指令，都会在每一次请求中被传进去。

context load 示意图：五个编号的请求，每一行包含代表不断增长的负载的方块，最前方的紫色方块每次都被重新发送

你仍然能享受到一些缓存，所以实际成本会比预期略低，但如果那东西并非每次请求都需要，让它一直占着窗口依然令人恼火。

context load 的两种成本（The Two Costs of Context Load）

你在为每次请求都带上这些 steering 指令而支付 token。 但还有第二种成本：你还在支付注意力。

你多加载的每一条额外指令，都会让其他每条指令的「声音」小一点，把 agent 往 dumb zone（愚蠢区）再推近一步。

注意力示意图：五个空盒子，箭头散布其上，在左侧密集聚集，越往右越稀疏

这两种成本合在一起——支付更多 token，同时把 agent 的注意力摊得更薄——就是我们所说的 context load（上下文负载）。每当你有一条 steering 指令，你都要想一想这条指令会带来多少 context load。

所以，当我们谈论 steering 时，想的不只是给 agent 写出好规则。关键在于搞清楚：哪些规则、哪些模式值得我们编码进 context window——因为我们添加的每一样东西，都要付出 context load 的代价。

push 与 point：两种 steering 策略（Push vs Point: Two Strategies for Steering）

每当想对 agent 做 steering，实际上只有两种选择：把指令 push（推送） 给它，或者 point（指向） 这条指令。

push：常开的 steering（Push: Always-On Steering）

想象 agent 的 context window 是一个盒子，我们的指令是躺在里面的一团黄色方块。把指令 push 给 agent，意味着这条 steering 指令永远开启。它在每一个 session 里都待在 context window 中。agent 不可能错过它，因为它本来就在 agent 的 context window 里。

这意味着，无论当前这个 turn 需不需要它，它都在消耗我们的 context load。

push 示意图：context window 内有一大块黄色方块，代表一条始终在场的 steering 指令

point：按需的 steering（Point: On-Demand Steering）

选择 point 时，你把 steering 指令放到 environment（环境）里的某个地方，然后在 context window 里放一行小字，仅仅用来指向它。这一行可以写成：「当你在做某一类工作时，就使用这些指令。」这一行就是一个 context pointer（上下文指针）。

它是待在 context window 里的一个指针：当 agent 需要时，就会顺着它走过去，把完整的指令拉进来。

在大多数 turn 里，一个 context pointer 几乎不花你任何成本。

point 示意图：context window 内有一个很小的黄色方块，一条黄色箭头向下指向窗口外的一整块黄色方块

策略 成本 可用性
push 每次请求成本都很高 始终在场
point 大多数 turn 里成本极低 仅在需要时

push 与 point 两种策略的并排对比：push 是 context window 内的一大块方块，point 则是窗口内的一个微小指针方块

push 式 steering 放在哪里：AGENTS.md（Where Pushed Steering Lives: AGENTS.md）

那么，怎么往 agent 的 context window 里 push 呢？一种技术是 AGENTS.md 文件。它通常位于项目根目录，harness（挽具）会在 session 开始时把它加载进 context window。

AGENTS.md 是一个跨 harness 的约定，所以无论你用的是什么工具，多半都认识它。最大的例外是 Claude Code——出于某种难以理解的原因，它管这文件叫 CLAUDE.md。我在课程里会叫它 AGENTS.md，不是因为迂腐，而是因为我希望有朝一日 CLAUDE.md 也能从善如流，跟上大部队。

push 式规则失灵时（When Pushed Rules Misfire）

我们现在理解了 push steering 规则的成本——它以 context load 的形式在每次请求上支付。但还有一个更大的问题：agent 分不清规则何时适用，于是它们常常会把你 push 进去的 steering 规则，套用到错误的场景上。

有人发来一个特别好笑的例子，讲 agent 执行指令时热心过了头。而且它并没有发生在 coding harness 里，而是在 claude.ai 上。

在 claude.ai 里，你可以打开设置，看到「instructions for Claude」（给 Claude 的指令），它的作用跟 AGENTS.md 文件一模一样：被 push 进 agent 的 context。

claude.ai 设置页面，显示 Instructions for Claude 区块

有人在他们的全局指令里写了类似这样的一条：

我在符合 PCI DSS 银行卡支付合规要求的环境下工作。任何涉及安全的事项都应标记出来。

然后他们问 agent 怎么烤巧克力蛋糕。agent 给了他们食谱，却在最后补了一条备注：鉴于他们在 PCI DSS 下处理信用卡，应当考虑这块巧克力蛋糕的安全影响。

浏览器显示一个标题为「Chocolate cake recipe」的 claude.ai 对话，agent 的回复在谈烘焙的 PCI DSS 合规影响

换句话说，这些 push 进去的规则会让 agent 做出奇怪的事。 我们最好确保自己使用 agent 的方式，跟放在里面的那些规则对得上。

过度 push 的流行病（The Epidemic of Over-Pushing）

这条建议会跟很多人当下的做法背道而驰。他们正把海量的指令 push 进 CLAUDE.md 或 AGENTS.md，而我认为正因如此，他们得到的结果反而更差。

眼下正流行一种「push 传染病」，无数 token 因此被浪费，这些 agent 背上了沉重的 context load。而我认为，你反而应该去研究 point 的技术。

在本课程中，实际的做法是：默认 point。 然后让 agent 自己决定要不要把这些指令拉进来。

本节余下的内容我们都会按这个思路展开。push 和 point 两种技术我们都会演示。有些场景你的确想 push；我们还会讲到 skill、讲到仓库内的文档，以及各种好用的技巧，让你既能 steer 自己的 agent，又不会 push 进太多 context load。

随堂测 · Quiz

你的项目里有一条编写数据库迁移（migration）的约定，大约每周才用上一次，而它足足有四十行。你会把它放在哪里？

  • 放在独立的文件里，在 AGENTS.md 中留一行 pointer
  • 直接内联进 AGENTS.md，让 agent 绝无可能错过
  • 写成一条笔记，等它相关时手动粘贴进 prompt

答案与解析

内联意味着在每个 session 的每一次 model provider request 上，都要为整整四十行买单，而这条规则一周才用一次——并且每多一条指令，其他指令都会更「安静」一点。手动粘贴则把成本转嫁到你身上，而恰恰在要紧的那一周，你一定会忘。pointer 在大多数 turn 里几乎零成本，工作需要时，agent 会自己把文件拉进来。

每个 session 开始时加载四十行，让你在每次请求上都支付 token。你要支付的第二种成本是什么？

  • 注意力：其他每条指令都变得更「安静」
  • 延迟：每个请求都要更久才有回音
  • 缓存：折扣彻底失效

答案与解析

缓存并没有消失——你仍然能享受一些，成本只是略有下降，所以失去的不是折扣。受拖累的也不是速度。是注意力：每多加载一条指令，其他指令都会更「安静」一点，agent 也被推得离 dumb zone 更近。

你的常开指令要求把任何涉及安全的事项标记出来。现在 agent 开始给跟安全毫无关系的工作附上合规备注。怎么修？

  • 把这条规则挪到一条 pointer 后面，并写明何时使用
  • 保持 push 状态，但补充它何时适用的措辞
  • 在更靠下的位置重述这条规则，让 agent 读到它

答案与解析

问题的根源是：一条 push 进去的规则摆在 agent 面前、对每个任务都生效，而 agent 分不清它何时适用。补充措辞改变不了它被 push 的事实，它照样在每次请求上消耗 context load，面对巧克力蛋糕问题时它依然在场。重述则让它在本该闭嘴的场景里嗓门更大。正确做法是把它放进 environment，只留一行指向它。

# 用 pointer 进行 steering（Steering With A Pointer）

Commit Map（提交地图）

  • pushed-migration-steps：本课起点——migration 步骤被 push 进 AGENTS.md，且 /writing-for-agents skill 可用
  • migration-steps-doc：查看我的解法——步骤被移入 docs/database-migrations.md，藏在一条 pointer 后面

在这个项目里，数据库 schema 值得格外小心。每当你修改 schema、新增一张表、改动一列，背后都藏着一个隐藏的第二步：你还必须更新 scripts/seed.ts——那个往数据库里填充初始数据的脚本。

如果你改了 schema 却忘了 seed 脚本，下一次 reseed 留给你的数据就不再匹配新的结构。Drizzle 给你的类型安全只到 schema 为止，DROP TABLE IF EXISTS 块里的裸 SQL 没有任何护栏，于是不匹配会悄无声息地溜过去，在下游把事情搞坏。

还有第二件事值得说清楚：在这个项目里，数据库是用完即弃的。它住在 data.db 里，已被 gitignore，里面除了 seed 数据什么都没有。你可以随意迁移、直接扔掉、从头 reseed。这些是实实在在的约束，是你会向前来报到的新同事交代的那种事。而 agent 不可能知道这些，除非你告诉它，因为 它们无法从代码里推导出来。

问题所在（The Problem）

最直接的做法是把所有这些步骤 push 进 AGENTS.md，让 agent 随时都有。但看看代价是什么。

每次请求都拖着完整的 migration 步骤。session 余下的每个 turn 都在为一个它此刻并不需要的文档支付 input token——说不定 agent 正在做一个跟数据库毫无关系的 UI 功能。这些步骤还要争夺 attention budget（注意力预算）。想象一个项目里有十套这样的指令，全部 push 进 context。成本会滚雪球式叠加。

doc-plus-pointer 模式（The Doc-Plus-Pointer Pattern）

你不需要每次请求都带着这些步骤。你需要的是每次请求都够得着它们。这是两回事。

把步骤从 AGENTS.md 里拿出来，给它们一份独立的文档。在 AGENTS.md 里只留一小行：改数据库 schema 时，先读这份文档。context load 变成一个句子。步骤只在 agent 顺着 pointer 走过去、真正需要时才加载。

这就是 doc-plus-pointer（文档加指针） 模式。context pointer 是 agent context 中的一个引用：它点明某份材料，并写明在什么条件下该去取。要让它起作用，需要两样东西：

  • 稳定的路径——agent 得知道去哪儿找它。
  • 清晰的 description——agent 得知道什么时候顺着它走才值得。一个光秃秃的路径是一个 agent 没有理由去用的 pointer。措辞要按任务实际出现的样子来写。

/writing-for-agents 这个 skill（The /writing-for-agents Skill）

给 agent 写好一份文档，本身就是一门手艺。你将使用 /writing-for-agents skill 来完成这件事。这个 skill 会把你脑子里的步骤变成 agent 能照着执行的文档：清晰、有序、没有废话。它正是为编写 AGENTS.md、以及编写那些藏在 pointer 背后的聚焦文档而造的。

待完成步骤（Steps To Complete）

  • 运行 npm run reset，拿到 /writing-for-agents skill

    这会把仓库重置到包含该 skill 的那个 commit。

  • 打开 /writing-for-agents skill，通读一遍

    弄明白它在要求什么，尤其是关于 context pointer 的部分，以及两种负载（context load 和 cognitive load，认知负载）。这就是你接下来要用的词汇。

  • 在仓库根目录新建一个 docs/ 文件夹

    你的 migration 步骤文档就放在这里。

  • 使用 /writing-for-agents，把 migration 步骤从 AGENTS.md 移到 docs/ 文件夹里一份名为 database-migrations.md 的新文档中

    skill 会引导你。让它把当前 AGENTS.md 里的步骤重构成一份独立成篇的文档。这份文档要能自立门户——它头顶上不会再有 AGENTS.md，所以把各级标题上提一级。

  • 用一行 pointer 取代 AGENTS.md 里的 migration 步骤

    这行 pointer 应该说清 agent 何时、为什么要去取那份文档。比如：「在做数据库 schema 变更时，查阅 docs/database-migrations.md 获取确切步骤。」

  • 做一个小而真实的 schema 变更，来测试这条 pointer

    打开一个 agent，让它对 schema 做一个简单的修改，比如给已有的表加一个非空列，或者加一个新字段。观察会发生什么。

    agent 应该会看到你在 AGENTS.md 里的那行 pointer，认出自己在做 schema 变更，然后从 docs/database-migrations.md 拉入完整文档。接着它应该照步骤执行：更新 schema、生成 migration、更新 scripts/seed.ts、reseed，最后 typecheck。

  • 验证变更是否成功

    确认 npm run db:seed 能无错跑完，npm run typecheck 通过，数据库里的数据与新 schema 相符。

  • 提交你的改动，完成后重置项目

    确认一切正常后，提交到你的分支。准备好继续往下走时，运行 npm run reset 回到初始状态。

理解 pointer（Understanding Pointers）

如你所见，一个 pointer 基本由两部分组成：

  1. 链接本身——真正进行指向的那个东西
  2. pointer 周围的文字——告诉 agent 什么时候该用它

记住：这才是真正会被 push 给 agent 的内容，只有真正需要时它才会去看那个文件。所以 pointer 上的 description 真的非常重要。

就我而言，我对这条 pointer 的 description 不算完全满意。它确实相当具体，比如「编辑这个特定文件之前先读；每当 schema 变更需要更新这个东西时读；或者当这个特定命令启动失败时读」。非常具体、非常明确，但我想把它放宽一点。

所以我要说：

Update the description of the pointer in AGENTS.md to be a bit broader to say: whenever we make a database change, follow these steps.

这样一来，agent 就有了非常明确的依据，清楚地知道什么时候需要照做。当然它也会自行判断——比如说，它可能看一眼文件名就说「好，database migrations，凡是需要数据库迁移的时候我就照做」。但这样写在我读来更舒服，而且也更短一点，这总是好事。

关键要点（The Key Takeaway）

所以，每当你要在全局范围里添加或实施 steering 时，我推荐用 point 而不是 push。

而这种「在仓库里放本地文档、藏在 pointer 后面」的模式，非常非常有效。

不过它确实有一些弱点，这正是接下来几课要探讨的。

干得漂亮，我们下一课见。

什么是 agent skill？（What Are Agent Skills?）

「文档配 pointer」这个模式很好用，但它撞上一个有趣的限制：它的全部东西都只待在一个仓库里。没有什么简单办法把它打包，交到你的队友手上。

你也没法把它们在项目之间搬运——每次都得手动抽取、手动粘贴。每一处使用都意味着手工复制文件，每个团队成员都得把这套活重做一遍。

skill：打包好的 pointer（Skills: A Pointer, Packaged）

skill 正是为这个问题而生的。skill 就是你前面见过的那套结构——一个指向文档的 pointer——但经过了打包和标准化。它是一个自包含的文件夹，干的是 doc-plus-pointer 那套活：steering 文件留在磁盘上，只在相关时才拉进来，全部捆成一个可移植、可分享的单元。

一个 skill 文件夹里有一个 SKILL.md 文件（主文档），外加它需要的任何辅助文件。skill 之所以可移植，靠的是这几点：

skill 文件夹结构，显示 SKILL.md 文件

  • 常驻的只有一行：skill 的 name 和 description
  • 其余都按需加载：正文和任何被链接的文件，只在 agent 伸手去取时才加载
  • 打包在一起：所有文件都在同一个文件夹里，随时可以分享

description 扮演着 agent 的 context pointer。它读一下 description，判断这个 skill 此刻是否相关；看完 description 之后，再决定要不要把这个 skill 加载进自己的 context window。

比如，一个叫 writing-for-agents 的 skill，description 是 "Writing documents for agents. Use when creating or editing skills, or modifying AGENTS.md or CLAUDE.md."（为 agent 撰写文档。在创建或编辑 skill、修改 AGENTS.md 或 CLAUDE.md 时使用。），它就清清楚楚地告诉了 agent 什么时候该取用它。

writing-for-agents skill，显示含 name 和 description 的 frontmatter

不止一个文件（More Than One File）

一个 skill 并不限于单个文件。skill 文件夹里的所有东西都会一起打包进去。所以一个 skill 可能包含：

  • SKILL.md（主入口）
  • 像 SKILL-MECHANICS.md 这样的辅助文件
  • 其他参考资料

主文件 SKILL.md 可以用 context pointer 指向这些辅助文件，agent 只在需要时才顺着这些链接走。这是 progressive disclosure（渐进式披露）再往下一层——在 agent 决定真正使用这个 skill 之前，它不用为辅助文件支付任何 context load。

比如你可以在 SKILL.md 里写：「当你正在写的文档本身是一个 skill 时，读 SKILL-MECHANICS.md，了解 frontmatter、调用方式的选择和 router skill。」

SKILL.md，显示指向 SKILL-MECHANICS.md 的 context pointer

这就形成了一个分层结构：

  • context window → name 和 description
  • name 和 description → SKILL.md
  • SKILL.md → SKILL-MECHANICS.md（及其他文件）

示意图：从 context window 到 SKILL.md 再到参考文件的分层结构

开放标准（The Open Standard）

skill 是一个开放标准，定义在 agentskills.io。这一点意义重大：为一个 agent 写的 skill，几乎可以原样工作在任何支持 skill 的 agent 上。它们是完全可移植的。

这种可移植性意味着你可以：

  • skill 只写一次
  • 与你的团队共享
  • 跨项目复用
  • 把海量信息打包进一个可移植的单元

调用 skill 的两种方式（Two Ways To Invoke A Skill）

skill 有两种主要的调用方式，二者在两种不同的负载之间做权衡：

调用方式 如何运作 Context Load Cognitive Load
model-invoked（model 自主调用） description 位于 context window 中。agent 能看到它、注意到它相关，然后自己把它拉进来。 较高 较低
user-invoked（用户手动调用） description 对 agent 隐藏。只有你自己能通过输入它的名字来调用。 零 较高（你得记住它）

两者的差别，归结为 skill frontmatter 里的一行。

model-invoked skill（Model-Invoked Skills）

把 description 留在 frontmatter 里，agent 就能自主发现这个 skill。它读到 description，认出什么时候相关，然后不用你提起就会自行调用。你当然还是可以自己输入 skill 的名字——model-invoked 永远包含手动调用这条路，它只是在之上多加了 agent 自主发现。

description 是这个 skill 的顶层 context pointer，它始终处于加载状态。这是一笔永久的 context load，但换来了自动可发现性。

user-invoked skill（User-Invoked Skills）

在 frontmatter 里加上 disable-model-invocation: true，description 就对 agent 隐藏了。这下只有你能按名字调用这个 skill——agent 完全够不着它，哪怕它本来能帮上忙。context load 为零，但你得记得这个 skill 存在，还得记得去用它。

一个 user-invoked skill 的 frontmatter 长这样：

---
name: handoff
description: Compact the current conversation into a handoff document for another agent to pick up.
disable-model-invocation: true
---

有了 disable-model-invocation: true，description 就从面向 agent 变成了面向人——这是留给你读的一行摘要，不是给 agent 解析的。

handoff skill 的 frontmatter，显示 disable-model-invocation: true

权衡（The Trade-Off）

在 model-invoked 和 user-invoked 之间做选择，是一种权衡：

  • 更多 model-invoked skill = 更高的 context load，但 agent 能自主发现它们
  • 更多 user-invoked skill = 额外 context load 为零，但你的认知负载更高

user-invoked skill 零 context load 这一点确实诱人。你可以囤一大堆，而不把 context window 撑得虚胖。这就是为什么很多个人 skill 集合都倾向于 user-invoked skill——就 context 而言，它们是「免费」的。

列出你的 skill（Listing Your Skills）

想看看你手头有哪些 skill，运行 /skills 命令。它会弹出一个菜单，列出你能用到的每个 skill 的 name 和 description。这就是你在支付的 context load——每个 model-invoked skill 一行。

/skills 命令输出，显示可用 skill 列表

在那份列表里，你能看出哪些是 user-invoked。比如：

  • grill-me 是 user-invoked（不向 agent 展示 description）
  • writing-for-agents 是 model-invoked（向 agent 展示 description）

user-invoked skill 可以通过输入名字来调用，跟任何命令一样。

skill：可移植的 pointer（Skills as Portable Pointers）

skill 不过是打包好的 pointer。它跟「仓库里一份文档加 AGENTS.md 里一行 pointer」是同一套结构，区别在于这里你可以：

  • 把它打包起来
  • 交给你的团队
  • 在网上分发
  • 在项目之间随身携带

「能轻松分享的东西」这个概念本身就充满力量。现在，你已经准备好动手造一个了。

对一个 agent 能自主发现的 skill 来说，始终待在 context window 里的是什么？

  • skill 的 name 和 description，就一行
  • SKILL.md 的全部内容，只是不含辅助文件
  • skill 文件夹里打包的每一个文件

答案与解析

SKILL.md 的正文和它链接到的任何文件，都只在 agent 伸手去取这个 skill 时才加载，所以两者都不会预先待在窗口里。打包是把文件放进同一个文件夹、好让 skill 可以被分享——它并不会把文件放进 context。每个可被发现的 skill 只占一行，这就是全部的常驻成本。

你写了一个大概每月才用两次的 skill，而且你知道自己会忘记它的存在。你会怎么写 frontmatter？

  • 保留 description，让 agent 能找到它
  • 设置 disable-model-invocation，用时按名字调用
  • 干脆把 skill 正文粘贴进 AGENTS.md 来代替它

答案与解析

把 description 藏起来的 context load 是零，但 agent 就完全够不着这个 skill 了，认知负载全落在你头上——对一个你注定会忘的 skill，恰恰是这一点会出问题。把正文粘进 AGENTS.md，则是每次请求都为整份文档付费，而不是一行。一行 description，换来的是 agent 有机会注意到它。

你的 SKILL.md 长出了很长一段讲 frontmatter 细节的内容，可它十次里只有一次用得上。这段内容该怎么处理？

  • 把它挪到第二个文件里，由 SKILL.md 用 pointer 指过去
  • 留在 SKILL.md 里，反正文件夹是整体打包的
  • 把它做成一个独立 skill，配自己的 description

答案与解析

留在 SKILL.md 里，意味着 skill 每次触发它都会加载，包括那九次用不上的场合——文件夹整体打包是为了分享，不是为了决定什么进窗口。拆成独立 skill 则又多出一行永久加载的 description。指向辅助文件的 pointer，在 agent 顺藤摸瓜之前分文不花。

User skills 还是 Project skills（User Vs Project Skills）

Skills 可以放在两个地方之一，而这个选择很重要。

skills 的两个层级（Two Levels for Skills）

第一个层级是你的用户目录 ~/.agents/skills。放在这里的 skill 是你个人的，走到哪跟到哪：你在这台机器上打开的每一个项目都能用到它。

第二个层级是项目本身，也就是项目里的 .agents/skills 文件夹。放在这里的 skill 会被提交进仓库，作用范围限定在这一个项目，但会共享给所有克隆这个仓库的人。

~/.agents/skills/ 下的用户级 skills 目录

一边是个人专属、随身携带；一边是团队共享、随仓库提交。 选择就在这两者之间。

skills 存放在哪里（Where Skills Live）

层级 位置 作用范围 共享方式
用户级 ~/.agents/skills/ 你个人专属 在你所有项目间全局通用
项目级 .agents/skills/ 限定于单个项目 共享给每一个克隆仓库的人

用户级的 skills 在两套约定下是同一回事——你也会看到有人说它们放在 ~/.claude/skills/。这两个路径在你的机器上指的是同一批 skills。

仓库内的项目级 skills 目录

在项目这一级，skills 会被提交进仓库。这意味着它们进入 git 历史，并自动共享给所有克隆该项目的人。到这个节点为止，ai-coding-crash-course 项目包含五个 skills：

如何选择：个人还是团队？（How to Choose: Personal or Team?）

规则是这样的：如果它是纯粹的个人效率小玩意——你偏好的工作方式、属于你自己的捷径——就放进你的用户目录。

一旦某个 skill 变成团队依赖的东西，变成「这个项目该怎么干活」的约定，它就该归项目所有。项目是更强的默认选项，因为：

  • 它有版本控制
  • 它随代码库一起演进
  • 每个克隆仓库的人自动获得它
  • 你永远不用提醒队友去安装任何东西

拿不准的时候，只要它关乎工作本身而不是你个人，就放进项目。

两种不同的风格（Two Different Flavors）

User 级 Project 级
个人的 随仓库提交的
全局的 单项目的
团队共有的

个人的（Personal）： 它只属于你，别人看不到，别人也不必使用它。

全局的（Global）： 它走到哪跟到哪。在用户目录装一次，你在这台机器上打开的每个项目里都能用，无需任何配置、无需复制。

随仓库提交的（Checked-in）： 这个 skill 成了仓库的一部分。它被 git 历史追踪，随项目一起走。

单项目的（Single-project）： 它不会跟到你的下一个项目，但它被限定在这一个项目里是有充分理由的。

团队共有的（Communal）： 每个参与这个项目的人都能为这个 skill 做贡献。skill 会随项目自动成长，团队里每个人都在长期建设它。

白板图：user 级与 project 级 skill 的特性对比

一个人干还是团队干？（Solo or Team?）

如果你基本是一个人干活，user 级 skills 大概率更方便，因为它们走到哪跟到哪。

一旦有了团队，或者有多个人向同一个项目做贡献，project 级 skills 就是正解。它会让所有在这个代码库里工作的人都实实在在受益。

# 导航指针（Navigation Pointers）

Commit Map（提交对照）

migration-steps-skill 本课起点：AGENTS.md 已被清空，迁移步骤挪进了一个 skill

seed-script-nav-pointer 查看我的解法：在 AGENTS.md 中加入了指向 scripts/seed.ts 的 navigation pointer

把你的代码库想象成一张卫星地图。agent 需要找东西的时候，它并没有鸟瞰视角，只能走在所谓的 **local roads（地方道路）**上。

agent 要扫描目录、一个一个打开文件、沿着引用链一路追下去，才能找到目标。它最终能到，但旅程很慢。沿途打开的每个文件都在往 context window 里添东西，消耗掉本可用于解决实际问题的 token。

但还有另一条路。**highway（高速公路）**和地方道路不是一回事。

Navigation pointer：为你的 agent 修高速公路（Navigation Pointers: Highways for Your Agent）

所谓 navigation pointer（导航指针），就是 AGENTS.md 里的短短一行，它把 agent 直接送往代码库中的重要位置，中间免掉一切扫描。它是一种有专门职责的 context pointer（上下文指针）：不告诉 agent 该做什么，而是告诉 agent 该去哪看。

你不会给每一个地方都修高速公路。那会把整个文件树都塞进 context，带来沉重的 context load（上下文负担）。你只给 agent 高频需要的地方修路；等它抵达附近，最后一段让它走 local roads 就好。

以 quiz 为例（The Quiz Example）

在代码库中搜索 quiz，命中多个文件

在代码库里搜索 "quiz"，agent 可能发现命中结果散落在很多文件里：

app/db/schema.ts
app/routes.ts
app/services/quizService.ts
scripts/seed.ts
...and more

接下来，agent 就得沿着引用链一条一条追下去，才能理解这个结构。

在 app/db/schema.ts 里，它可能会发现：

id: integer("id").primaryKey({ autoIncrement: true }),
lessonId: integer("lesson_id")
.notNull()
.references(() => lessons.id),

export const quizQuestions = sqliteTable("quiz_questions", {

agent 只能顺着这些引用链一条一条走。有了 navigation pointer，它清清楚楚知道自己该去哪。

给 seed 脚本加一条 navigation pointer（Adding a Navigation Pointer to the Seed Script）

最近几课里，数据库迁移老是坏，原因是 agent 没有更新 scripts/seed.ts。seed 脚本是一个关键文件，agent 经常需要落到它上面，但搜索时却偏偏容易漏掉它。

让 agent 往 AGENTS.md 里加一条 navigation pointer

解法就是加一条 navigation pointer。与其让 agent 自己探索时碰巧发现 seed 脚本，不如在 AGENTS.md 里直接把它指过去：

# Navigation

- `scripts/seed.ts` - the definition of the database's starting data, rebuilt from scratch on every `npm run db:seed`. Every schema change lands here too.

这轻量到了极点：三行，一个列表项。但它给了 agent 关键的一臂之力，因为这是一个难以发现、却非改不可的文件。

当 agent 在改 schema 时，它现在知道了：「每一次 schema 改动都会落到 seed 脚本上。」这就是那个触发器。agent 会主动去找它，而不需要某个 skill 被触发。

每个新建的 skill 都有一些不摆在前面的依赖：

  2. 如果它在 engineering/ 或 productivity/ 里，就必须在 .claude-plugin/plugin.json 中有一条记录
  3. 如果它在 engineering/ 或 productivity/ 里，就必须有一份面向人类的文档页，位于 docs/<bucket>/<skill-name>.md
  4. 如果它在 engineering/ 或 productivity/ 里，就必须在顶层的 README.md 中被引用
  5. misc/、personal/、in-progress/、deprecated/ 里的 skill 则绝不能出现在 plugin manifest 或文档里

这些依赖在文件系统上是看不见的。agent 扫描目录树时，不会明白为什么 productivity/ 里新建一个 skill，还要在另外三个地方补记录。

Every skill in `engineering/` or `productivity/` (the promoted buckets) must
have a reference in the top-level `README.md` and an entry in
`.claude-plugin/plugin.json`'s `skills` array. Skills in `misc/`, `personal/`,
`in-progress/`, and `deprecated/` must not appear in either.

过期指针的代价（The Cost of Stale Pointers）

navigation pointer 会过期。危险在这里：你移动了一个文件，却忘了更新 AGENTS.md 里指向它的指针——这条指针不会报错，也不会警告你，它只是继续指着老位置。

于是你就修了一条通往 nowhere 的高速公路。agent 信任你 steering files（引导文件）里的信息，并且照着行动。一条过期指针会把它带到错误的地方，还在它琢磨「文件怎么不在这」的时候白白烧掉 token。

规则很简单：每当你改动项目结构，就去检查你的 navigation pointer。一条过期的高速公路比没有高速公路更糟，因为 agent 是真的信它。

单条提示词里的 navigation pointer（Navigation Pointers in a Single Prompt）

用 @-mention 把文件加进 context

同样的思路在单条消息里也成立。当你在提示词里 @-mention 一个文件时，你其实是在创建一条只管一轮对话的 navigation pointer：

范围 机制 位置
每个 session navigation pointer AGENTS.md
一轮对话 @-mention 聊天消息

两者都是把 agent 直接送往某个文件、免掉扫描。AGENTS.md 里的 navigation pointer 是永久的，作用于每一个任务；@-mention 只作用于一条提示词。同一套机制，不同的作用范围。

什么时候该用 navigation pointer（When to Use Navigation Pointers）

navigation pointer 适合这样的文件：

  • 靠扫描很难发现
  • 解决问题时非改不可
  • 属于那些不直观的工作流的一部分

别给所有东西都加。指针越少，代码库变动时你要维护的就越少。但在那些结构举足轻重、依赖又看不见的仓库里，一份带 navigation pointer 的好 AGENTS.md，决定了一个 agent 是高效探索，还是反复漏掉关键文件。

# 修剪（Pruning）

把文件放进项目仓库、让所有人共同贡献，这种做法有一个大问题。

它们只增不减。它们总是越变越大，极少变小。里面每条规则当初都有理由加进来，而几乎没有一条会被删掉。一个文件从五行开始，长到 500 行，再到 1000 行。

原因是心理层面的。加一条规则感觉成本低、感觉安全，尤其当你在给一份集体文档做贡献的时候。删一条规则，感觉像在宣称「这条规则不重要了」，像是在踩别人的劳动成果。

但 pruning（修剪）这个理念很重要。Pruning 就是定期回头过一遍文件，把里面的东西剪掉。 它对降低整体 context load 至关重要。

现实世界里的 AGENTS.md，几乎每一份都远远、远远超出了它该有的体量。好消息是，你可以学会有效地修剪它们。

Pruning 工具箱（The Pruning Toolkit）

你需要一个办法，逐行决定什么留下。解法是三项测试，你可以对任何 steering 文件逐一执行。这三项测试构成了 pruning 工具箱。

测试 定义
Single Source Of Truth（唯一事实来源） 每条事实都应该只住在一个权威位置
Sediment（沉积物） 曾经为真、如今已不为真的行
No-Op（无效指令） 对 agent 行为毫无影响的指令

任何通不过这三项测试的东西，都没有挣到它在 context window 里的位置。剪掉它，你会发现你的 steering 水平大幅提升。

测试 1：Single Source Of Truth（Test 1: Single Source Of Truth）

agent 需要的每一条事实，都应该只住在一个权威位置。每条事实，只留一个 single source of truth（唯一事实来源）。

这意味着要避免重复。你可能在 AGENTS.md 里写了条规则，然后又把一个略有出入的版本贴进了某份文档。也许它们在不同地方被分别编辑，或者来自不同的 pull request。现在，完全相同的信息有了多个、还常常互相打架的来源。

当重复很多的时候，agent 常常分不清哪份是现行版本，于是信了错的那份。文件特别长的时候，甚至同一个文件内部也会出现重复。

重复的代价（The Cost of Duplication）

重复从三个方面坑你：

  1. 维护成本——每次要改行为，你得在多个地方都改一遍。

  2. context load——你付着 token，把同一句话说了一遍又一遍。

  3. 存在感——被重复的信息会比没被重复的信息更显眼，于是它的权重远高于它真实的实际重要性。

这意味着被重复的内容，会淹没其他同样重要、只是没被重复的信息。一条事实有三个家，就是一条你不再说了算的事实。

每条事实只放一个地方，其他所有地方都指向那里。

测试 2：Sediment（Test 2: Sediment）

Sediment（沉积物）是第二个让 steering 文件腐烂的东西。sediment 本质上是个心理问题，是团队与这些文件相处方式的问题。

AGENTS.md 里的 sediment 会随时间层层堆积，因为加感觉安全，删感觉冒险。任何一份没有严格 pruning 纪律的 steering 文件都会陷入沉积，变得越来越长、越来越长、越来越长。

每条规则在你写下它的那天都合理。但项目在前进：库被换掉了，约定变了，你当年防的那个 bug 修好了。而你为它写的规则还在。没人删它。它沉到文件底部，把 agent 往一个已经不复存在的世界拽。

这意味着你的 AGENTS.md 会慢慢对越来越多的任务失去相关性。沉积意味着大量无关的东西挤进 context window，占着 context、拖着 agent 的表现往下走。

识别 Sediment（Identifying Sediment）

sediment 特别危险，因为它大概率曾经是对的。它可能对过一阵子，也可能到现在仍然正确、只是并不适用于所有场景。你必须毫不留情地删掉它，或者把它挪到某条指针背后。

对每一行都问一句：它现在还是真的吗？

测试 3：No-Op（Test 3: No-Ops）

No-op 大概是其中最阴险的问题：最容易加进来，最难删出去。

no-op 是一条什么都不做的指令，对输出毫无影响。它以两种方式发生：

  • 模型默认就会这么做
  • 在那条 steering 指令的特定语境下，它什么作用也没有

想象你写了一个 /implement skill，里面有条指令说「写一条详细的 commit message」。这条指令真的需要吗？删掉它会怎样？它还会写出好的 commit message 吗？多半会。

所以你在付 context load，只为告诉它一件它无论如何都会做的事。

侦测 No-Op（Detecting No-Ops）

去掉 no-op 的办法很简单：把它删掉，然后看行为有没有变。 如果没变，那一行八成就是 no-op，可以删。

这项测试只问一个问题：这一行相对于默认行为，改变了什么吗？

一条指令可以完全切合当下情境，却依然是个 no-op。 它可以是真的、切题的，却依然不值一个 token，因为 agent 根本不需要你告诉它。

而 no-op 不是免费的。它还在 context 里，还在付 context load，还在稀释它周围那些真正要紧的行。

综合运用（Putting It Together）

这就是 pruning 工具箱——对每份 steering 文件执行的三项测试：

  1. 这条指令是否被重复了，破坏了 single source of truth？
  2. 这条指令是不是一块 sediment——曾经为真，如今已不为真？
  3. 这一行是不是 no-op？ 它真的有改变行为的作用吗？

任何通不过这三项测试的东西，都没有挣到它在 context window 里的位置。它只是在让你白付 context load，换不来任何收益。

剪掉它，你会发现你的 steering 水平大幅提升。

通不过其中任何一项测试的东西，都应该剪掉。对着留下来的部分，问自己：每一行都在每个 session 里挣到了自己的位置吗？

动手修剪：解法（Trying Out Pruning Solution）

Commit Map（提交对照）

init-generated-claude-md 本课起点：/init 生成的那个臃肿的 AGENTS.md

面对一份臃肿的 AGENTS.md，首先要考虑的是重复。不只是文件内部的重复，还有代码库里那些随手就能查到的来源里的重复。

找出重复项（Finding the Duplicates）

最显眼的重复出现在开发命令部分。

开发命令部分：npm run dev、npm build 和 npm start

你会看到 npm run dev、npm run build、npm run start 列在那里，但这些命令本来就在 package.json 里：

{
"scripts": {
"dev": "react-router dev",
"build": "react-router build",
"start": "react-router-serve ./build/server/index.js"
}
}

对 agent 来说，在 package.json 里找到这些命令毫不费力。

纪律（The Discipline）

真正的纪律，不在于写更多的 steering 文档，而在于让你已有的内容保持诚实。

当你为 agent 写指引时，你是在制造一项维护负担。你留下的每一行都需要保持最新。你做出的每一个断言都需要保持为真。文件越长，就越容易腐烂、偏离真实的代码库、变成负资产。

Pruning 的过程逼你问一些扎心的问题：

  • agent 是不是早就知道这个？
  • 这个是不是别处已经有文档了？
  • 这是真坑还是 no-op？
  • 这句话一个月之后还为真吗？

等你做完，留下来的东西精瘦而诚实。这就是「真正能引导行为的指引」和「agent 学会无视的噪音」之间的区别。

Claude Code 的 automatic memory（Claude Code's Automatic Memory）

还有一类 steering 来源我们没有讨论过，那就是 agent 为自己写的那一种。

automatic memory 的工作原理（How Automatic Memory Works）

大多数 harness 都自带一个 memory system（记忆系统），agent 会往里写、从里读，未必需要你开口。工作过程中，agent 会注意到值得记住的东西。于是它会注意到你对它行为的某次纠正、你表达过的某个偏好，或是一条关于你希望活儿怎么干的实事，然后把它存进本地某个文件里。

这些文件会在之后的 session 里被读进 context window。取决于具体 harness，方式要么像 AGENTS.md 那样直接推入，要么以指针的形式。

这意味着，理论上，agent 会在你不用 steer 它的情况下，慢慢拼出「你喜欢怎么干活」的图景。它在给自己掌舵。它在抢方向盘。

找到 automatic memory（Finding Automatic Memory）

Claude Code 的 /memory 命令：auto-memory 已开启

在 Claude Code 里，在这里运行 /memory 就能看到：automatic memory 是开着的。

我们可以看到，它用 CLAUDE.md 作为 memory 的文件名——这挺有意思。另外还有一个 auto-memory 部分。

Chrome 中打开的 auto-memory 文件夹，里面有 MEMORY.md 文件

按下「open auto-memory folder」之后，它居然是在 Chrome 里打开的（有点怪），里面有一个小小的 MEMORY.md 文件。

auto-memory 文件存放在你的仓库之外，位于 Claude Code 的每项目状态目录里，以当前工作目录为键。这就是为什么它永远不会出现在 git status 里，也永远不会被 code review。

auto-memory 里装了什么（What Auto-Memory Contains）

MEMORY.md 里面是一份索引，指向 agent 写下的各个 memory 文件。这里有一条是这么写的：

- Editing course repos skill - this is a course repo; the governing skill lives in personal-wiki, not here

这是 agent 在把它自己的记忆念给你听。它在留意你项目里的事实，先存起来留给之后的 session。

被链接的那个 memory 文件本身，用的形状和 skill 一模一样：YAML frontmatter 带着 name 和 description，然后是正文。agent 其实在你背后给自己写 skill。

过期记忆的问题（The Problem With Stale Memory）

问题在这里：automatic memory 就像自动沉积的 sediment。它是一份自己会写自己的沉积物，堆起一层层过期内容，而 agent 极少会把它们删掉。

agent 写下条目，却不删除。所以文件只增不减。里面每一行都在每个 session 里付着 context load。你曾有、后来又改掉的一个偏好，会变成 agent 一直相信的错误假设。适配过某一个任务的一条提示，会变成跟着你进每一个后续任务的规则。

而且因为这些行不是你写的，你更不可能会进去修剪它们。

看一下 memory 的 metadata，你能看到创建它的那个原始 session，往往已是几周之前。而它从那时起，就一直在 context window 里无声地搭着车。

我的建议（The Recommendation）

我已经给你看过我修剪 AGENTS.md 有多狠，也说过我多不喜欢让 agent 给自己掌舵——就因为那些 no-op 和它往 context window 里堆的垃圾。automatic memory 恰恰就是这个问题，只不过现在发生时，连放什么东西进去都不由你决定。

所以我的建议是：进到 auto-memory 设置里，把它关掉。

在 Claude Code 设置里关闭 auto-memory

从此不再有任何记忆被存下来。这也让 context window 变小了，因为创建记忆的那个工具不再出现在里面。真是轻松。

很多人问我 memory system 的事，问该不该把它们加进自己的配置。我的回答是：不要。你作为用户，应该掌控记忆如何被创建、steering 如何进行。

因为如果你放任这些 automatic memory 一层层攒下去，你就是在往自己的 context 里堆积没用的 sediment。

这一节的全部主旨就是「有意识地 steering」：挑选什么配得上 context 里的位置，并让它保持最新。automatic memory 与此背道而驰。它是你没选择的 steering，在你看不见的地方累积。
