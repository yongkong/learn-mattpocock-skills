## 一、grilling:把模糊逼成共识的访谈法

它是 `/grill-me`、`/grill-with-docs`、`/improve-codebase-architecture` 内部共同运行的方法。三个机制(SKILL.md 原文);术语的查词条版见词典([Grilling · 追问式访谈](/dictionary)):

### 1. Design tree(设计树)

把计划画成一棵树:每个决策下面挂着依赖它的子决策。概念来自 Frederick Brooks《The Design of Design》。<Cite>(来源:[5 agent skills I use every day](https://www.aihero.dev/5-agent-skills-i-use-every-day))</Cite>例如「做搜索页」分叉成「高级搜索还是简单文本框」;选了高级搜索,又分叉出过滤器、排序……直到每个分支都走完。

### 2. Frontier(边界),一轮一轮问

不是想到什么问什么。每轮只问<strong>前提已解决</strong>的问题——答案不依赖本轮其他未决问题的那批。一次问完整个 frontier,每题编号、附推荐答案(❓Q1 …… ➡️ 推荐);你的回答会重塑这棵树:已定的决策把 frontier 向外推,解锁原本被卡住的下游问题,然后重算、开下一轮。

### 3. 事实和决策严格分工

**查事实是 agent 的工作**:frontier 上有需要查环境的问题(文件、代码、文档),它派 sub-agent 去查,绝不问你。**做决策是你的工作**:每个决策摆到你面前,等你拍板。一轮 16 个问题很常见,复杂特性 30~50 个也有。

结束条件:frontier 为空——设计树每个分支都走过,没有<strong>被默默假设</strong>的东西;而且在你确认「共识达成」之前,它不许动手做任何事。<Cite>(来源:本地插件 [productivity/grilling/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md))</Cite>

<Callout>
    <strong>一个值得留意的关联机制:</strong>
    wayfinder 的决策地图里也有一个 frontier(开放、无阻塞、未被认领的工单)。同一个词不是巧合——wayfinder
    就是项目尺度的 grilling:把「一棵没走完的设计树」摊成工单慢慢走(见 [0004](/lessons/0004))。
</Callout>

## 二、domain-modeling:磨利项目的统一语言

它管的是<strong>领域模型</strong>——不是数据库模型,而是:这个项目的业务概念词汇表 + 关键决策记录。落地为两个文件:`GLOSSARY.md`(纯词汇表,<strong>零实现细节</strong>,不是 spec 也不是草稿本)和 `docs/adr/`(架构决策记录)。文件原名 `CONTEXT.md`,v1.3 起更名:名字源自 DDD 的「限界上下文」,但过于含糊,agent 该触发时没触发;而文件实际早已收缩成一份纯词汇表——`GLOSSARY.md` 名副其实。旧仓库迁移就是一条 `git mv CONTEXT.md GLOSSARY.md`(团队要在一个所有人都拉取的提交里一起改,否则先升级的人的 agent 会在旁边新建一个空文件)。

四个具体动作(SKILL.md 原文):

1. **对照词汇表挑战**——你用了和 GLOSSARY.md 冲突的词,立刻指出:"你的词汇表定义 cancellation 是 X,你现在说的像 Y,到底是哪个?"
2. **逼模糊词变精确**——"你一直说 account,到底是指 Customer 还是 User?这是两个东西。"
3. **用具体场景压测**——编造边界场景逼你说清概念边界:"VIP 用户在下单瞬间被降级,这单还享折扣吗?"
4. **和代码交叉验证**——你说支持部分取消,代码却只能整单取消,它把矛盾摆上桌:"哪个是对的?"

术语一旦敲定,<strong>当场写进 GLOSSARY.md</strong>,不攒批。ADR 则很克制,要同时满足三个条件才提议:<strong>难以逆转</strong>(改主意代价大)+ <strong>没有上下文会让人困惑</strong>(未来读者会问为什么)+ <strong>真实权衡的结果</strong>(存在过真选项)。三者缺一,就不立 ADR。<Cite>(来源:本地插件 [engineering/domain-modeling/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/domain-modeling/SKILL.md))</Cite>

v1.3 还放宽了它的触发条件:不只是被 grill-with-docs 调用——<strong>你在讨论代码库术语、或直接编写/编辑 GLOSSARY.md 与 ADR 时,它也会自己进场</strong>。词汇表的维护从「访谈的副产品」变成了随时可触发的独立纪律。

为什么值得单独一个技能?整套体系的心法是:agent 没有记忆。统一语言就是给 agent 的共享记忆——词汇表写清楚后,grilling 提问、写 spec、命名测试、/wait-what 重新解释消息,全都用同一套词。

## 三、codebase-design:整套体系的设计词典

参考层里最特殊的一个:它不执行任何流程,只提供<strong>统一的说话方式</strong>。SKILL.md 开头就禁止换词——不许说 component、service、API、boundary——因为一致的语言本身就是目的。

### 核心主张:深模块(deep module)

**小接口后面藏大量行为,放在干净的 seam 上,通过接口就能测试。**支付模块只暴露 `pay(order, method)`,内部自己处理渠道路由、重试、幂等、对账——深;暴露 8 个方法、每个原样转发 SDK 调用——浅,接口几乎和实现一样复杂,调用者什么都躲不掉。

六个关键词:**Module**(有接口有实现的东西,尺度无关:函数、类、包、跨层切片都行)、**Interface**(调用者必须知道的<strong>一切</strong>:类型签名 + 不变量 + 顺序约束 + 错误模式 + 配置 + 性能特征)、**Seam**(接缝:不修改此处就能改变行为的位置)、**Adapter**(在 seam 上满足接口的具体实现,描述角色而非内部)、**Leverage**(深度给<strong>调用者</strong>的回报:一份实现被 N 个调用点和 M 个测试复用)、**Locality**(深度给<strong>维护者</strong>的回报:改动、bug、验证集中一处,修一次 = 修好所有)。

### 三个马上能用的判断工具

- **删除测试(deletion test)**:想象删掉这个模块——复杂度凭空消失 = 它只是透传(浅);复杂度在 N 个调用点重新冒出来 = 它在挣自己的饭钱。
- **接口即测试面**:调用者和测试跨同一个 seam;想"钻到接口背后去测",多半是模块形状做错了。
- **一个 adapter 是假想 seam,两个才是真 seam**:没有真实变化的东西,不要提前引入接缝。

词源是 Ousterhout《A Philosophy of Software Design》,但 SKILL.md 末尾明确拒绝了"深度 = 实现行数÷接口行数"的量化定义(会鼓励灌水),改用<strong>深度即杠杆</strong>。消费方:`/improve-codebase-architecture` 用它扫描 deepening 机会;`/tdd` 在接口形状有争议时点名查它——原话:"it is a reference to consult, not a session to run"(词典是用来查的,不是用来跑的)。<Cite>(来源:本地插件 [engineering/codebase-design/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/codebase-design/SKILL.md))</Cite>

## 四、tdd:让循环产出「值得留的测试」

SKILL.md 的自我定位:循环本身(red → green)很简单,这个技能的价值是<strong>让循环产出的测试值得保留</strong>。文章里说得更直白:<em>「把 TDD 做好,是提升 agent 代码质量最一致的方法。」</em><Cite>([5 agent skills](https://www.aihero.dev/5-agent-skills-i-use-every-day))</Cite>

<Flow>
  <Step cmd="Red">先写一个失败的测试——只写一个,针对提前约定好的 seam</Step>
  <Step cmd="Green">写恰好够让这个测试通过的实现,不预设未来的测试,不加投机功能</Step>
  <Step cmd="重复">一个 seam、一个测试、一份最小实现 = 一轮;每轮是一个 tracer bullet(曳光弹),根据上一轮学到的调整下一轮</Step>
</Flow>

### 测试写在哪?——seam 上,而且是「预先约定」的 seam

测试放在 seam(公共边界),永远不伸进内部。更严格的是:开写任何测试之前,agent 必须先列出「本次测哪些 seams」并<strong>跟你确认</strong>——不可能什么都测,提前约定才让测试力气花在关键路径上。开写前它还会读 GLOSSARY.md,让测试命名用项目的领域词汇——domain-modeling 的产物在这里被消费。

### 三个反模式

- **implementation-coupled**:mock 内部合作者、测私有方法、从侧门验证(绕过接口直接查数据库)。识别标志:<strong>重构后测试挂了,但行为没变</strong>。
- **tautological(同义反复)**:断言用和代码一样的方式重算期望值——`expect(add(a,b)).toBe(a+b)`。期望值必须来自独立事实源:已知正确的字面量、手算过的例子、spec。
- **horizontal slicing(横切)**:先把所有测试写完再写实现。批量测试验证的是<strong>想象的行为</strong>。正确姿势是 vertical slice:一个测试 → 一份实现 → 循环。

<Callout>
    <strong>一个反直觉细节:</strong>
    经典口诀是 red-green-<em>refactor</em>,但这个技能明说「重构不属于循环」——重构归 code-review
    阶段管。实现循环只管红变绿,评审阶段再统一找坏味道。这防止了 agent 在循环里一边加功能一边大改结构。
</Callout>

## 五、pr:让 PR 正文一眼可审

参考层里最新的一个(v1.3):model-invoked——你(或实现技能)要开 PR 时,模型自动拉它进场,把 PR 正文按一个固定骨架写出来。它解决的问题很具体:agent 写的 PR 描述常常是一句「实现了 XX 特性」,审查者没法从一句话里看出改动形状、也没法判断往哪儿看。模板三段(SKILL.md 原文):

1. **Summary(摘要)**:用<strong>最小的那张图</strong>说清改动的关键——逻辑用伪代码、运行时控制流用调用树、UI 结构用组件树、重构用文件树、交互/数据流用 Mermaid、纯改动点用 diff。只保留能回答「这次改动是什么」的调用、文件和状态,不堆全量细节。
2. **Evidence(证据)**:<strong>before / after</strong> 的硬证据——改之前测试怎么红、改之后怎么绿。截图是 S 级(环境支持且改动可视时),执行证据是 A 级(测试结果、控制台输出)。这是在挡 agent 那句最危险的「我读了代码,应该能跑」。
3. **Merge Danger(合并危险)**:这是一扇<strong>单向门还是双向门</strong>(roll back 便宜吗?有没有破坏性、难回退的动作?)加<strong>爆炸半径</strong>(一个词:影响面在哪——布局位移、消费方破坏、移动端?)——告诉审查者该把注意力花在哪。

正文措辞要用 `GLOSSARY.md` 里的领域语言——参考层内部又一次互相咬合:domain-modeling 攒下的词汇,在 PR 正文这里被消费。可视化的模板改编自 Dex Horthy 的 show-me 技能(上游 CREDITS.md 有署名)。<Cite>(来源:本地插件 [engineering/pr/SKILL.md](https://github.com/mattpocock/skills/blob/main/skills/engineering/pr/SKILL.md))</Cite>作者对它的评价很高:他见过<strong>最可靠的 model-invoked 技能之一</strong>——因为「写 PR body」这个触发时机极其明确,模板又硬。

## 五台发动机怎么咬合

一条真实的链:`/grill-with-docs` 调用 grilling(frontier 访谈)<strong>+ domain-modeling</strong>(顺手沉淀 GLOSSARY.md/ADR);访谈聊到接口形状,codebase-design 的词汇进场;共识交给 `/to-spec` 写成 spec;`/implement` 拿到工单后调用 tdd,在 spec 约定的 seam 上 red-green;`/code-review` 收尾,重构在这时才发生;开 PR 时 `/pr` 自动进场,用 GLOSSARY.md 的语言写正文。参考层的五个技能,就这样各自被主流程的不同站点调用——<strong>你不直接敲它们,但每次主流程都在踩它们</strong>。
